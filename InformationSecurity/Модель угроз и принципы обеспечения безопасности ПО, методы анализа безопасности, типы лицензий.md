## **1. Модель угроз (Threat Modeling)**

**Модель угроз** — это систематический подход к идентификации, оценке и документированию потенциальных угроз безопасности программного обеспечения или системы.

### **Цели моделирования угроз:**
- Выявление уязвимостей на этапе проектирования
- Приоритизация рисков безопасности
- Определение контрмер и требований безопасности
- Создание основы для тестирования на проникновение

### **Основные этапы моделирования угроз:**

**1. Определение активов (Assets)**  
Что защищаем? Данные пользователей, интеллектуальная собственность, репутация, доступность сервиса.

**2. Создание диаграммы потока данных (DFD)**  
Визуализация компонентов системы, потоков данных, границ доверия, точек входа/выхода.

**3. Идентификация угроз**  
Использование методологий:
- **STRIDE** (Microsoft): Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege
- **PASTA** (Risk-centric): Процессно-ориентированный подход
- **LINDDUN** (Для конфиденциальности): Утечка, неотказуемость и т.д.

**4. Оценка и ранжирование угроз**  
Использование матриц риска (вероятность × воздействие), например, **DREAD**:
- Damage potential (Ущерб)
- Reproducibility (Воспроизводимость)
- Exploitability (Эксплуатируемость)
- Affected users (Затронутые пользователи)
- Discoverability (Обнаружаемость)

**5. Определение контрмер**  
Выбор методов смягчения для каждой угрозы.

## **2. Принципы обеспечения безопасности ПО (Secure Development Lifecycle - SDL)**

### **Основополагающие принципы:**

**1. Принцип наименьших привилегий (Least Privilege)**  
Каждый компонент системы должен работать с минимально необходимыми правами для выполнения своих функций.

**2. Защита в глубину (Defense in Depth)**  
Многоуровневая защита: если один слой провален, другие должны продолжать защищать.

**3. Простота и минимализм (Simplicity and Minimalism)**  
Чем сложнее система, тем больше потенциальных уязвимостей.

**4. Отказ в безопасности по умолчанию (Fail-Safe Defaults)**  
По умолчанию система должна находиться в самом безопасном состоянии.

**5. Полная посредническая проверка (Complete Mediation)**  
Каждый доступ к ресурсу должен проверяться на соответствие политикам безопасности.

**6. Разделение обязанностей (Separation of Duties)**  
Критичные операции должны требовать участия нескольких субъектов.

**7. Экономия механизмов (Economy of Mechanism)**  
Механизмы безопасности должны быть простыми и проверяемыми.

**8. Психологическая приемлемость (Psychological Acceptability)**  
Система безопасности не должна усложнять работу легитимным пользователям.

**9. Открытое проектирование (Open Design)**  
Безопасность не должна зависеть от сокрытия архитектуры или алгоритмов.

**10. Учет человеческого фактора**  
Самые слабые звенья в безопасности — люди.

### **Принципы безопасного кодирования:**
- Проверка всех входных данных (Input Validation)
- Экранирование выходных данных (Output Encoding)
- Безопасная работа с аутентификацией и сессиями
- Защита от инъекций (SQL, XSS, Command)
- Безопасная работа с памятью (предотвращение переполнений буфера)
- Использование криптографии правильно

## **3. Методы анализа безопасности ПО**

### **Статический анализ безопасности (SAST - Static Application Security Testing)**
Анализ исходного кода без его выполнения.

**Методы:**
- **Анализ потока данных** — отслеживание недоверенных данных через программу
- **Символьное выполнение** — анализ всех возможных путей выполнения
- **Анализ уязвимых шаблонов** — поиск известных шаблонов уязвимостей

**Инструменты:** SonarQube, Checkmarx, Fortify, Coverity, PVS-Studio

**Преимущества:** Раннее обнаружение, полный охват кода  
**Недостатки:** Ложные срабатывания, не обнаруживает runtime-уязвимости

### **Динамический анализ безопасности (DAST - Dynamic Application Security Testing)**
Тестирование работающего приложения.

**Методы:**
- **Фаззинг (Fuzzing)** — подача случайных/некорректных данных на вход
- **Сканирование уязвимостей** — автоматизированное тестирование на известные уязвимости
- **Ручное тестирование** — исследование специалистами по безопасности

**Инструменты:** OWASP ZAP, Burp Suite, Nessus, Acunetix

**Преимущества:** Обнаружение runtime-проблем, проверка конфигурации  
**Недостатки:** Неполный охват кода, требует работающего приложения

### **Интерактивный анализ безопасности (IAST - Interactive Application Security Testing)**
Комбинация SAST и DAST, работающая изнутри приложения.

**Методы:** Инструментирование кода, мониторинг выполнения

**Преимущества:** Высокая точность, низкий уровень ложных срабатываний  
**Недостатки:** Сложность настройки, влияние на производительность

### **Анализ зависимостей (SCA - Software Composition Analysis)**
Проверка сторонних библиотек и компонентов.

**Методы:** Сканирование на известные уязвимости (CVE), лицензионный анализ

**Инструменты:** Snyk, Black Duck, OWASP Dependency-Check

**Важность:** >80% современного кода состоит из сторонних компонентов

### **Ручной анализ и код-ревью**
- **Аудит кода (Code Review)** — проверка кода коллегами
- **Тестирование на проникновение (Penetration Testing)** — имитация атак реальными специалистами
- **Red Team vs Blue Team** — упражнения по кибербезопасности

### **Моделирование угроз в процессе разработки**
- Включение в Agile/DevOps процессы
- Использование автоматизированных пайплайнов (DevSecOps)
- Непрерывная безопасность (Continuous Security)

## **4. Типы лицензий на ПО**

### **A. Проприетарное (собственническое) ПО**
**Характеристики:** Закрытый исходный код, ограничения на использование, модификацию, распространение.

**Типы лицензий:**
1. **Коробочная (Perpetual License)** — бессрочное использование конкретной версии
2. **Подписка (Subscription)** — оплата за период использования
3. **Пользовательская (Per User/Seat)** — лицензия на каждого пользователя
4. **Серверная (Per Server/CPU)** — лицензия на сервер или процессор
5. **Ограниченная (Trial/Demo)** — временная или с ограниченным функционалом

**Примеры:** Microsoft Windows, Oracle Database, Adobe Photoshop

### **B. Свободное и открытое ПО (FOSS)**

#### **Свободное ПО (Free Software, по определению FSF):**
Четыре степени свободы:
1. **Запуск** программы с любой целью
2. **Изучение** и модификация исходного кода
3. **Распространение** копий
4. **Распространение** модифицированных версий

#### **Открытое ПО (Open Source, по определению OSI):**
10 критериев, включая свободное распространение, доступ к исходному коду, право на модификации.

### **C. Основные типы лицензий открытого ПО:**

#### **1. Разрешительные (Permissive) лицензии:**
Минимальные ограничения, можно использовать в проприетарном ПО.
- **MIT License** — очень простая, требует только сохранения уведомления об авторских правах
- **Apache License 2.0** — включает патентную оговорку
- **BSD License** (2/3-пунктная) — варианты с разным уровнем ограничений

#### **2. Копилефтные (Copyleft) лицензии:**
Требуют, чтобы производные работы распространялись на тех же условиях.
- **GPL (General Public License)**:
  - **GPLv2** — требует открытия кода производных работ
  - **GPLv3** — дополнительно защищает от "tivoization" (железных ограничений) и патентных атак
- **LGPL (Lesser GPL)** — более мягкая, позволяет линкование с проприетарным кодом
- **AGPL (Affero GPL)** — требует открытия кода даже при использовании через сеть (SaaS)

#### **3. Специализированные лицензии:**
- **Creative Commons** — для контента, разные варианты (CC BY, CC BY-SA, CC BY-NC)
- **Mozilla Public License 2.0** — слабый копилефт, как LGPL
- **Eclipse Public License** — бизнес-ориентированная

### **D. Лицензионные риски и комплаенс:**

**Основные риски:**
1. **Нарушение лицензионных условий** — судебные иски
2. **"Заражение" кода** — нечаянное применение копилефта к собственному коду
3. **Патентные претензии** — особенно при использовании кода компаний, ведущих патентные войны

**Меры управления:**
- **Лицензионный комплаенс** — отслеживание всех используемых компонентов
- **Политика использования ПО** — внутренние правила в организации
- **Инструменты сканирования** — автоматическое обнаружение лицензий
- **Юридическая экспертиза** — особенно для критичных проектов

### **E. Тенденции в лицензировании:**
1. **Рост популярности разрешительных лицензий** (MIT, Apache) в экосистеме JavaScript, Go, Rust
2. **Усиление копилефта** в ответ на облачные сервисы (AGPL, SSPL от MongoDB, BSL от CockroachDB)
3. **Гибридные модели** — открытое ядро + платные расширения
4. **Source-available** — код доступен для чтения, но не под открытой лицензией

## **5. Интеграция безопасности в жизненный цикл разработки (DevSecOps)**

### **Современный подход:**
1. **Shift Left** — перенос безопасности на ранние этапы разработки
2. **Automation** — автоматизация проверок безопасности
3. **Continuous Security** — непрерывный мониторинг и улучшение
4. **Culture** — формирование культуры безопасности в команде

### **Практические шаги:**
- Статический анализ в CI/CD пайплайне
- Регулярное обновление зависимостей
- Автоматизированное сканирование на уязвимости
- Обучение разработчиков безопасному кодированию
- Регулярные аудиты и пентесты

---

## **Заключение**

Безопасность ПО — это не отдельная фаза, а непрерывный процесс, охватывающий весь жизненный цикл разработки. Эффективная безопасность требует:
1. **Системного подхода** через моделирование угроз
2. **Следования принципам** безопасного проектирования
3. **Комбинации методов анализа** (статического, динамического, ручного)
4. **Внимания к лицензионным вопросам** для избежания юридических рисков
5. **Интеграции в процессы разработки** (DevSecOps)

Ключевой тренд — **проактивная безопасность**, когда проблемы обнаруживаются и устраняются до попадания в production, а не реагирование на инциденты постфактум.
