## **1. Концепция доверия в информационной безопасности**

**Доверие (Trust)** — это уверенность в том, что система, пользователь или процесс будет вести себя ожидаемым образом в определённых условиях.

### **Основные модели доверия:**

**1. Модель явного доверия (Explicit Trust)**
- Доверие явно устанавливается администратором
- Пример: статические списки доступа (ACL), сертификаты в хранилище доверенных

**2. Модель неявного доверия (Implicit Trust)**
- Доверие предполагается по умолчанию
- Пример: внутренняя сеть компании, где все устройства считаются доверенными

**3. Иерархическая модель доверия (Hierarchical Trust)**
- Цепочка доверия через посредников
- Пример: PKI (Инфраструктура открытых ключей) с корневыми и промежуточными центрами сертификации

**4. Распределённая модель доверия (Distributed/Web of Trust)**
- Доверие устанавливается через рекомендации и связи
- Пример: PGP (Pretty Good Privacy), где пользователи подписывают ключи друг друга

**5. Модель нулевого доверия (Zero Trust)**
- Основной принцип: "Никогда не доверяй, всегда проверяй"
- Каждый запрос аутентифицируется и авторизуется независимо от источника
- Микропериметры и сегментация вместо единой границы

### **Проблемы концепции доверия:**
- **Перенос доверия (Trust Transitivity)** — если A доверяет B, а B доверяет C, должно ли A доверять C?
- **Эрозия доверия** — со временем уровень доверия должен пересматриваться
- **Масштабируемость** — управление доверием в больших системах

## **2. Аутентификация с открытым ключом (Public Key Authentication)**

### **Основные концепции:**

**Асимметричная криптография** использует пару ключей:
- **Закрытый ключ (Private Key)** — хранится в секрете, используется для подписи и расшифровки
- **Открытый ключ (Public Key)** — распространяется свободно, используется для проверки подписи и шифрования

### **Принцип работы:**

**Для аутентификации (например, в SSH):**
1. Сервер хранит открытые ключи пользователей
2. Клиент доказывает владение закрытым ключом, подписывая случайный challenge
3. Сервер проверяет подпись с помощью открытого ключа

**Для шифрования:**
1. Отправитель шифрует данные открытым ключом получателя
2. Получатель расшифровывает данные своим закрытым ключом

### **Преимущества:**
- Не требует передачи секретов по сети
- Устойчивость к пассивному прослушиванию
- Возможность цифровых подписей и non-repudiation

### **Недостатки:**
- Вычислительно сложнее симметричного шифрования
- Управление ключами (распределение, отзыв, хранение)
- Риск компрометации закрытого ключа

### **Практические применения:**
- **SSH-ключи** для доступа к серверам
- **SSL/TLS** для веб-сайтов
- **S/MIME** и **PGP** для email
- **Кодовая подпись** для ПО

## **3. SSL/TLS (Secure Sockets Layer / Transport Layer Security)**

**SSL/TLS** — криптографические протоколы для защиты передачи данных поверх TCP.

### **Эволюция протоколов:**
- **SSL 1.0** — не выпущен публично
- **SSL 2.0** (1995) — серьёзные уязвимости
- **SSL 3.0** (1996) — уязвимость POODLE (2014)
- **TLS 1.0** (1999) — основан на SSL 3.0
- **TLS 1.1** (2006) — защита от CBC-атак
- **TLS 1.2** (2008) — современный стандарт
- **TLS 1.3** (2018) — улучшенная безопасность и производительность

### **Процесс установления соединения (Handshake):**

**В TLS 1.2:**
1. **Client Hello** — клиент предлагает поддерживаемые алгоритмы
2. **Server Hello** — сервер выбирает алгоритмы, отправляет сертификат
3. **Проверка сертификата** — клиент проверяет сертификат через PKI
4. **Обмен ключами** — клиент шифрует pre-master key открытым ключом сервера
5. **Вывод ключей** — обе стороны вычисляют общие сессионные ключи
6. **Finished** — обмен зашифрованными сообщениями для проверки

**В TLS 1.3:** Упрощённый handshake (1-RTT или 0-RTT), удалены небезопасные алгоритмы

### **Компоненты SSL/TLS:**
1. **Аутентификация** — через сертификаты X.509
2. **Шифрование** — симметричное (AES, ChaCha20) после handshake
3. **Целостность** — HMAC или AEAD (Authenticated Encryption with Associated Data)

### **Уязвимости и атаки:**
- **POODLE** — против SSL 3.0
- **BEAST** — против TLS 1.0
- **CRIME, BREACH** — компрессионные атаки
- **Heartbleed** — уязвимость в OpenSSL (утечка памяти)
- **DROWN** — атака через поддержку SSL 2.0

### **Best Practices:**
- Отключить устаревшие протоколы (SSL 2.0/3.0, TLS 1.0/1.1)
- Использовать современные шифры (AES-GCM, ChaCha20-Poly1305)
- Правильно настраивать сертификаты (домен, срок действия)
- Регулярно обновлять ПО (OpenSSL, библиотеки)

## **4. WEP (Wired Equivalent Privacy)**

**WEP** — первый протокол безопасности для беспроводных сетей 802.11 (1999).

### **Принцип работы:**
1. **Общий ключ** — все устройства в сети используют один ключ (40/104-битный)
2. **Инициализационный вектор (IV)** — 24-битное значение, добавляемое к ключу
3. **RC4 stream cipher** — генерация ключевого потока для шифрования
4. **CRC-32** — для проверки целостности (ICV)

### **Критические уязвимости:**

**1. Слабость RC4:**
- Статистические смещения в выходном потоке
- Возможность восстановления ключа после анализа достаточного количества трафика

**2. Короткий IV (24 бита):**
- Повторяется каждые ~16 миллионов пакетов
- В активной сети — за несколько часов

**3. Статический ключ:**
- Нет механизма ротации ключей
- Сложность управления при увольнении сотрудников

**4. Атака на аутентификацию:**
- Возможность восстановления ключа через анализ challenge-response

**5. Уязвимость CRC-32:**
- Линейная функция, позволяет модифицировать пакеты без обнаружения

### **Основные атаки:**
- **Пассивное прослушивание** — восстановление ключа из трафика
- **Active injection** — внедрение пакетов для ускорения атаки
- **Dictionary attacks** — для слабых паролей
- **FMS attack** — именная атака Fluhrer, Mantin, Shamir (2001)

### **Итог по WEP:**
- **Полностью сломан** с 2001 года
- **Не должен использоваться** в любых условиях
- Взлом занимает **минуты** с современным оборудованием
- Заменён на **WPA**, затем **WPA2/WPA3**

## **5. 802.1X (Port-Based Network Access Control)**

**802.1X** — стандарт контроля доступа к сетям на основе портов, обеспечивающий аутентификацию устройств перед предоставлением сетевого доступа.

### **Архитектура и компоненты:**

**1. Supplicant (Клиент)** — устройство, запрашивающее доступ
- Пример: ноутбук сотрудника, телефон

**2. Authenticator (Аутентификатор)** — контролирует физический доступ
- Пример: коммутатор, точка доступа Wi-Fi, VPN-шлюз
- Действует как **прокси** между клиентом и сервером

**3. Authentication Server (Сервер аутентификации)** — проверяет учётные данные
- Обычно **RADIUS** сервер (FreeRADIUS, Microsoft NPS)
- Может использовать базы: Active Directory, LDAP, SQL

### **Протокол EAP (Extensible Authentication Protocol)**

**EAP** — framework для методов аутентификации, работает поверх 802.1X.

**Популярные методы EAP:**

**1. EAP-MD5** — устаревший, только односторонняя аутентификация, уязвим

**2. EAP-TLS (Transport Layer Security)** — наиболее безопасный
- Взаимная аутентификация через сертификаты
- Требует PKI для управления сертификатами

**3. EAP-TTLS (Tunneled TLS)** — создаёт туннель TLS, внутри которого можно использовать другие методы (PAP, CHAP, MS-CHAPv2)

**4. PEAP (Protected EAP)** — Microsoft, похож на EAP-TTLS
- **PEAP-MS-CHAPv2** — распространён в Windows-средах
- **PEAP-TLS** — с сертификатами

**5. EAP-FAST** — Cisco, использует Protected Access Credential (PAC)

**6. EAP-SIM/AKA** — для мобильных сетей (использует SIM-карты)

### **Процесс аутентификации 802.1X:**

1. **Инициализация** — клиент подключается к порту
2. **EAPOL-Start** — клиент инициирует аутентификацию
3. **Identity Request/Response** — запрос и передача идентификатора
4. **Аутентификация через RADIUS** — коммутатор передаёт данные серверу
5. **Success/Reject** — решение сервера
6. **Открытие порта** — при успехе, порт переводится в авторизованное состояние

### **Преимущества 802.1X:**
1. **Централизованное управление** — политики на сервере
2. **Динамическое назначение VLAN** — на основе атрибутов пользователя
3. **Безопасность на уровне устройства** — аутентификация до получения IP
4. **Гибкость** — поддержка различных методов аутентификации
5. **Масштабируемость** — для больших организаций

### **Сценарии использования:**
- **Корпоративные сети** — проводные и беспроводные
- **Гостевой доступ** — отдельные VLAN для гостей
- **BYOD (Bring Your Own Device)** — контроль личных устройств
- **IoT безопасность** — аутентификация устройств Интернета вещей

### **Сложности внедрения:**
1. **Сложность настройки** — требуется инфраструктура (RADIUS, возможно PKI)
2. **Проблемы с устаревшими устройствами** — без поддержки 802.1X
3. **Требует квалифицированного персонала**
4. **Риск отказа в обслуживании** при проблемах с сервером

### **802.1X для Wi-Fi (WPA/WPA2 Enterprise):**
- **WPA/WPA2-Enterprise** использует 802.1X для аутентификации
- Каждый пользователь получает уникальный сессионный ключ
- Гораздо безопаснее, чем Pre-Shared Key (PSK)

## **6. Сравнение и эволюция технологий**

### **Эволюция безопасности Wi-Fi:**
1. **WEP (1999)** → Сломан, не использовать
2. **WPA (2003)** → Временное решение с TKIP
3. **WPA2 (2004)** → CCMP с AES, обязателен с 2006
4. **WPA3 (2018)** → SAE, 192-битная безопасность, защита от офлайн-атак

### **SSL/TLS vs WEP:**
- **SSL/TLS** — развивающийся стандарт с постоянными улучшениями
- **WEP** — заморожен в небезопасном состоянии, заменён полностью

### **Интеграция технологий:**
- **802.1X + EAP-TLS** → используется в корпоративных Wi-Fi сетях
- **PKI** → основа для SSL/TLS и EAP-TLS
- **Zero Trust** → может использовать 802.1X для микросегментации

### **Современные тенденции:**
1. **Отказ от паролей** — в пользу сертификатов, биометрии
2. **Continuous authentication** — постоянная проверка в сессии
3. **Post-quantum cryptography** — подготовка к квантовым компьютерам
4. **Passwordless Wi-Fi** — WPA3 Enhanced Open (OWE)

## **Заключение**

**Концепция доверия** эволюционирует от неявных моделей к **Zero Trust**, где каждый запрос проверяется независимо.

**Аутентификация с открытым ключом** стала фундаментом современных протоколов безопасности, устранив необходимость передачи секретов.

**SSL/TLS** показывает пример успешной эволюции протокола безопасности через постоянное улучшение и обновление.

**WEP** служит предостережением о том, что происходит, когда безопасность не развивается в ответ на найденные уязвимости.

**802.1X** демонстрирует эффективность централизованного контроля доступа и гибкость через framework EAP.

**Ключевой вывод:** Безопасность — это процесс, а не состояние. Протоколы и технологии должны постоянно развиваться, адаптироваться к новым угрозам и заменяться при обнаружении критических уязвимостей.
