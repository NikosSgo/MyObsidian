Асинхронность в Rust — это модель неблокирующего выполнения, основанная на `async/await`, `Future` и внешнем рантайме. Она предназначена прежде всего для высоконагруженных I/O-задач (сети, файлы, таймеры), а не для ускорения CPU-вычислений.

В основе лежит трейт `Future`. Любая асинхронная операция в Rust — это значение, реализующее `Future`, у которого есть метод `poll`. Этот метод не блокирует поток, а сообщает: либо результат готов (`Poll::Ready`), либо нужно подождать (`Poll::Pending`). Сам `poll` напрямую пользователь почти никогда не вызывает — этим занимается исполнитель (executor).

Ключевое слово `async` превращает функцию или блок кода в объект `Future`. Вызов `async fn` не выполняет код сразу, а лишь создаёт future. Реальное выполнение начинается только когда future передаётся в рантайм и опрашивается. Ключевое слово `await` приостанавливает текущую future до тех пор, пока ожидаемая операция не станет готовой, при этом поток не блокируется.

Пример минимального синтаксиса:

```rust
async fn fetch() -> String {
    "data".to_string()
}

async fn process() {
    let data = fetch().await;
    println!("{data}");
}
```

Здесь `fetch()` возвращает future, а `await` говорит рантайму: «возобнови выполнение, когда future завершится».

Важно понимать, что стандартная библиотека Rust не содержит асинхронного рантайма. Для запуска `async`-кода нужен внешний исполнитель. На практике используются:

– [[Tokio]] — де-факто стандарт для серверов и сетевых приложений  
– async-std — более “std-подобный”, но менее распространён  
– smol — минималистичный рантайм

Рантайм управляет пулом потоков и очередью задач. Асинхронные задачи (`tasks`) гораздо легче системных потоков и могут исчисляться десятками тысяч.

Параллелизм и асинхронность — не одно и то же. Асинхронность решает проблему ожидания (I/O wait), а не параллельных вычислений. Если внутри `async`-кода выполнить тяжёлый CPU-расчёт, он заблокирует поток рантайма. Для этого используют `spawn_blocking` или отдельные thread-pool’ы.

Ошибки в асинхронном коде обрабатываются так же, как и в синхронном — через `Result` и `?`. Отличие лишь в том, что ошибка «приезжает» после `await`.

Отдельно стоит отметить ограничения модели. `async`-функции порождают state machine, из-за чего:  
– нельзя просто так использовать рекурсию без `Box`  
– типы future могут быть очень сложными  
– `Send` / `!Send` имеет критическое значение при работе с многопоточными executors

Когда асинхронность оправдана:  
– HTTP-серверы, клиенты, прокси  
– работа с БД, файловой системой, сокетами  
– системы с большим количеством одновременных соединений

Когда она не нужна:  
– простые CLI-утилиты  
– чисто CPU-bound алгоритмы  
– код, где простота важнее масштабируемости
