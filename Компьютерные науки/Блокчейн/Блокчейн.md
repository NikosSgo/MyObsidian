1. по своей сути блокчейн - это программа, запускаемая одновременно на многих компьютерах, ее состояние синхронизируется между всеми узлами. централизованная сеть хранит все данные в базе, и имеют права доступа на их изменение, удаление, что является проблемой централизации. блокчейн является базой, которая единолично никому не принадлежит, информация о любых данных полностью открыта. также блокчейн не требует и не хранит личные данные пользователей. взаимодействие с блокчейном для обычного пользователя начинается ссоздания кошелька (с точки зрения реализации кошелек является парой приватного и публичного ключа). пользователь напрямую блокчейн не видит и не трогает. он взаимодействует через кошелёк / приложение, rpc-узел, визуальный интерфейс.

  
2. закрытый ключ генерируется  случайно. открытый ключ зависит от закрытого и создается на его основе с помощью односторонней операции, например разложение на множители (RSA), либо эллиптических кривых ECDSA, Ed25519. адрес является математическим представлением открытого ключа, полученный с помощью хеш-функций

  

     на примере Ton:

     **Private key** — закрытый ключ (32 байта)

     В Ed25519 закрытый ключ — это 32 байта случайных данных  

    (или 64 байта, если вместе с расширенным seed).

    f1a32c8d4e...  (64 hex символа)

  

     **Public key** — открытый ключ (32 байта)

     Получается из закрытого ключа через криптографическую функцию Ed25519.

     **Address** — адрес (формируется из публичного ключа и данных о кошельке)

     адрес TON — это хеш всего состояния смарт-контракта кошелька, а не просто хеш ключа.

  
  

 3. корректную работу сети обеспечивают валидаторы, чем больше тем лучше, пока существует валидатор, сеть живет. сообщение (неподтвержденная транзакция) о желании выполнить операции, например перевод другому пользователю, попадает одному из валидаторов. подобные транзакции, которые ещё не включены в блок, попадают в мемпул — это буфер ожидания для транзакций. у каждого узла свой локальный мемпул. мемпулы постепенно "выравниваются", но не становятся полностью одинаковыми.  после того как узел принял и проверил корректность, транзакция добавляется в локальный мемпул узла. после приёма узел рассылает транзакцию соседям (p2p gossip). в итоге транзакция постепенно появляется в мемпулах множества узлов. в момент создания блока валидатор/майнер: смотрит свой локальный мемпул, выбирает транзакции по приоритету. после публикации блока узлы обновляют свои мемпулы: убирают включённые транзакции. транзакция выполняет код смарт контракта и фиксируется в истории блокчейна. транзакция имеет собственный хеш, по которому можно выполнять поиск по блокчейну.

  

4. **хеш** всегда является постоянным для конкретной строки и обладает фиксированной длинной, получить из хеша оригинальные данные невозможно, это односторонняя функция. блок содержит в себе некоторое кол-во транзакий, блоки создаются спустя какой-то промежуток времени. в большинстве блокчейнов создаются пустые блоки, если нет новых транзакций. хешем блока является результат суммирования всех полей, входящих в информацию блока. изменение любых данных в блоке приведет к изменению хеша блока и сделает все последующие блоки невалидными.

  
  

 5. ассиметричное **шифрование**. производится с помощью ключа открытого, результат шифрования не является хешем, потому что он может быть расшифрован обратно, но только с использованием приватного ключа. вместе с сообщение в блокчейне отправляется подпись пользователя, подпись получается путем применения данных сообщения и приватного ключа отправителя. далее с помощью восстановления через подпись и содержимое получается публичный ключ, а далее путем хеширования получается адрес. полученный адрес сравнивается с адресов отправителя в сообщении.

  

 6. **seed-фраза** — это человеко-читаемое представление твоего закрытого ключа, которое используется для восстановления кошелька. Это набор слов. Каждое слово выбирается из списка BIP39 (2048 слов). Фраза представляет собой один большой случайный бинарный код. генерация ключей детерминирована, поэтому при вводе той seed фразы возможно восстановить доступ к своему кошельку.

  

7. **gas** — это единица измерения вычислительной работы, которую нужно выполнить для обработки транзакции или вызова смарт-контракта в блокчейне. чтобы выполнить транзакцию в блокчейне, валидаторы тратят CPU, память, дисковую запись. gas = плата за эти вычисления. Когда ты отправляешь транзакцию, ты указываешь: gas limit — максимум газа, который готов потратить, gas price — цена за единицу газа в нативной монете сети. Стоимость транзакции = `gas used × gas price`.

8. **консенсус** —  майнер собирает блок из своего локального мемпула. затем он хеширует заголовок. побеждает тот, чей хеш удовлетворил условию. его блок публикуется, проверяется узлами и включается в цепь. заголовок блока не прямо содержит все транзакции, зато содержит их сжатое криптографическое представление — Merkle root. первоначально транзакция попадает на rpc-узел приложения кошелька. далее рассылается уже другим узла. одна транзакция может находиться в мемпулах множества узлов, чтобы в случае сбоя одного узла, транзакция не потерялась. после того как один блок включил блок в цепочку, остальные узлы при проверке блока, удаляют из своего мемпула уже использованные транзакции.

Сначала кошелёк генерирует энтропию, то есть криптографически случайный набор битов. В примере используется 128 бит, или 16 байт. Это исходный секретный материал, от качества которого зависит безопасность всего кошелька. Если энтропия будет предсказуемой или недостаточно случайной, злоумышленник теоретически сможет восстановить приватный ключ. Затем от этой энтропии вычисляется SHA-256-хеш. Сам хеш здесь нужен не для создания адреса напрямую, а для получения контрольной суммы. При энтропии 128 бит по стандарту BIP-39 берутся первые 4 бита SHA-256-хеша, потому что длина контрольной суммы равна длине энтропии, делённой на 32. Поэтому получается 128 бит энтропии плюс 4 бита контрольной суммы, всего 132 бита. Эти 132 бита делятся на группы по 11 бит, потому что словарь BIP-39 содержит 2048 слов, а 2048 — это 2 в 11 степени. Каждая группа из 11 бит соответствует одному слову из словаря. Так из 132 бит получается 12 слов мнемонической фразы, например: legal winner thank и так далее. Мнемоническая фраза является удобной для человека формой записи исходной энтропии с контрольной суммой, а не просто обычным паролем.

  

После этого мнемоническая фраза преобразуется в seed. Для этого используется функция PBKDF2-HMAC-SHA512 с 2048 итерациями. В качестве salt используется строка `"mnemonic"` плюс дополнительная passphrase, если пользователь её задал. Если passphrase не используется, то salt фактически равен просто `"mnemonic"`. На выходе получается seed длиной 64 байта, то есть 512 бит. Этот seed затем используется кошельком для получения приватных ключей. На схеме показано упрощение: первые 32 байта seed берутся как приватный ключ. Но в реальных Bitcoin HD-кошельках обычно так не делают. На практике чаще используется стандарт BIP-32: из seed получается мастер-ключ и chain code, а затем из них по определённому пути деривации создаются дочерние приватные ключи. Поэтому более точная цепочка выглядит так: mnemonic превращается в seed, seed превращается в BIP-32 master private key, затем через derivation path получается конкретный приватный ключ для конкретного адреса.

  

Дальше начинается правая часть схемы: из приватного ключа получается публичный ключ, а из публичного ключа — адрес. Приватный ключ в Bitcoin — это число размером 32 байта, то есть 256 бит, используемое в алгоритме ECDSA на эллиптической кривой secp256k1. Этот ключ должен оставаться полностью секретным, потому что человек, знающий приватный ключ, может подписывать транзакции и тратить средства. Из приватного ключа вычисляется публичный ключ по формуле Q = G × privateKey, где G — базовая точка эллиптической кривой, privateKey — секретное число, а Q — публичный ключ. Эта операция работает в одну сторону: публичный ключ легко получить из приватного, но практически невозможно получить приватный ключ из публичного. Публичный ключ может быть представлен в несжатом формате длиной 65 байт или в сжатом формате длиной 33 байта. На схеме указан вариант с публичным ключом длиной 65 байт.

  

Затем публичный ключ хешируется. Сначала от него считается SHA-256, после чего результат дополнительно хешируется алгоритмом RIPEMD-160. Такая комбинация называется HASH160 и записывается как RIPEMD160(SHA256(publicKey)). Результат имеет длину 20 байт, или 160 бит. Далее к этому хешу добавляется байт версии. Для обычного legacy Bitcoin-адреса в основной сети используется байт версии 0x00. Этот байт показывает, к какой сети и какому типу адреса относится результат. Например, 0x00 используется для Bitcoin mainnet P2PKH-адресов, которые начинаются с единицы. После добавления версии вычисляется контрольная сумма: от данных version + HASH160 дважды считается SHA-256, затем берутся первые 4 байта результата. Эта checksum нужна для проверки ошибок при вводе или копировании адреса. После этого вся структура, состоящая из байта версии, HASH160 и контрольной суммы, кодируется в Base58Check. В результате получается привычный Bitcoin-адрес, например 1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa. Такой адрес можно передавать другим людям для получения средств, а вот мнемоническую фразу, seed и приватный ключ нельзя никому показывать, потому что их утечка означает потерю контроля над кошельком.
