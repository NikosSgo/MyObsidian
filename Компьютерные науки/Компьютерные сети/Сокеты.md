**Сокет** (*socket*) — программная конечная точка обмена данными. Он связывает процесс с выбранным сетевым протоколом и хранит адреса, порты, состояние и очереди данных.

Сокет не является отдельным уровнем перед TCP/IP. Это **API и объект ядра**, через который приложение подключается к сетевому стеку.

```text
приложение
    ↓ файловый дескриптор сокета
TCP или UDP
    ↓
IPv4 или IPv6
    ↓
сетевой интерфейс
```

## Что создаётся первым

1. Приложение вызывает `socket()` и указывает семейство адресов, тип и протокол.
2. Ядро создаёт объект сокета и связывает его с реализацией TCP, UDP или другого протокола.
3. `connect()`, `send()` или `sendto()` передают этому протоколу адреса и данные.
4. TCP/UDP добавляет транспортный заголовок и передаёт результат IPv4 или IPv6.
5. IP ищет маршрут, добавляет IP-заголовок и передаёт пакет сетевому интерфейсу.

То есть объект сокета действительно создаётся раньше первого пакета, но сам сокет не обрабатывает маршрутизацию и не заменяет TCP/IP.

## Семейство адресов, тип и протокол

```c
int socket(int domain, int type, int protocol);
```

- `domain` — семейство адресов `AF_*`: выбирает пространство адресов и сетевую подсистему.
- `type` — способ обмена: поток, дейтаграммы, raw-доступ и другие варианты.
- `protocol` — конкретный протокол внутри выбранной комбинации; обычно можно указать `0`.

Семейство адресов задаёт не только вид адреса. Оно определяет, что вообще означает адрес, какая структура `sockaddr_*` используется и какой обработчик ядра создаст сокет.

```c
socket(AF_INET,  SOCK_STREAM, 0);  // TCP поверх IPv4
socket(AF_INET6, SOCK_STREAM, 0);  // TCP поверх IPv6
socket(AF_INET,  SOCK_DGRAM,  0);  // UDP поверх IPv4
socket(AF_INET6, SOCK_DGRAM,  0);  // UDP поверх IPv6
```

- `AF_INET` или `AF_INET6` выбирает семейство IP.
- `SOCK_STREAM` выбирает потоковый транспорт — обычно [[TCP]].
- `SOCK_DGRAM` выбирает дейтаграммы — обычно [[UDP]].
- Третий аргумент `0` просит ядро выбрать стандартный протокол для этой пары.

Raw socket создаётся как `SOCK_RAW` и позволяет приложению работать ближе к IP, но требует дополнительных прав.

### Основные семейства

- **`AF_UNIX` / `AF_LOCAL`** — обмен между процессами на одном компьютере без IP. Адрес задаётся путём или именем в `struct sockaddr_un`.
- **`AF_INET`** — IPv4. Использует `struct sockaddr_in`, в которой находятся IPv4-адрес и 16-битный порт.
- **`AF_INET6`** — IPv6. Использует `struct sockaddr_in6`: IPv6-адрес, порт и при необходимости `scope_id` интерфейса.
- **`AF_NETLINK`** — обмен между user space и ядром. Через него работают, например, `ip route`, `ip address` и другие инструменты настройки сети.
- **`AF_PACKET`** — отправка и получение Ethernet-кадров на канальном уровне. Использует `struct sockaddr_ll`; применяется в анализаторах пакетов и требует специальных прав.
- **`AF_CAN`** — Controller Area Network, используемая в автомобилях и встраиваемых системах.
- **`AF_BLUETOOTH`** — низкоуровневые протоколы Bluetooth.
- **`AF_VSOCK`** — связь между виртуальной машиной и гипервизором без обычной IP-сети.
- **`AF_XDP`** — высокопроизводительный обмен кадрами между очередью сетевого интерфейса и user space через общую память UMEM.
- **`AF_ALG`** — доступ к криптографическому API ядра через интерфейс сокетов; сетевые пакеты при этом не используются.

`AF_UNSPEC` означает «семейство не задано». Его обычно используют в `getaddrinfo()` для поиска и IPv4-, и IPv6-адресов, а не для создания обычного рабочего сокета.

### Структуры адресов

Системные вызовы принимают общий указатель `struct sockaddr *`, но фактически приложение передаёт структуру выбранного семейства:

```text
struct sockaddr
  ├─ sockaddr_in    → AF_INET:  IPv4 + порт
  ├─ sockaddr_in6   → AF_INET6: IPv6 + порт
  ├─ sockaddr_un    → AF_UNIX:  локальный путь/имя
  ├─ sockaddr_nl    → AF_NETLINK
  └─ sockaddr_ll    → AF_PACKET: интерфейс и L2-адрес
```

Во всех структурах первым находится поле семейства, например `sin_family = AF_INET`. Отдельный аргумент длины нужен потому, что структуры имеют разный размер. Для универсального хранения адреса используют `struct sockaddr_storage`.

Пример IPv4-адреса:

```c
struct sockaddr_in addr = {
    .sin_family = AF_INET,
    .sin_port = htons(443)
};

inet_pton(AF_INET, "203.0.113.10", &addr.sin_addr);
connect(fd, (struct sockaddr *)&addr, sizeof(addr));
```

`htons()` переводит порт в сетевой порядок байтов, а `inet_pton()` преобразует текстовый IP-адрес в бинарное представление.

### Как семейство выбирается в ядре

Каждое поддерживаемое семейство регистрирует `struct net_proto_family`. Когда приложение вызывает `socket()`, функция `__sock_create()` в `net/socket.c` находит обработчик по номеру `AF_*` и вызывает его метод `create`.

```text
socket(AF_INET, ...)
  ↓
__sock_create()
  ↓ таблица net_families[AF_INET]
inet_family_ops.create = inet_create()
  ↓
выбор TCP, UDP или RAW IP
```

Основные реализации:

- `AF_INET` — `net/ipv4/af_inet.c`;
- `AF_INET6` — `net/ipv6/af_inet6.c`;
- `AF_UNIX` — `net/unix/af_unix.c`;
- `AF_NETLINK` — `net/netlink/af_netlink.c`;
- `AF_PACKET` — `net/packet/af_packet.c`;
- `AF_VSOCK` — `net/vmw_vsock/af_vsock.c`;
- `AF_XDP` — `net/xdp/xsk.c`.

После выбора семейства его функция `create` проверяет `type` и `protocol`. Поэтому `AF_INET` может создать TCP-, UDP- или raw-сокет, но неподдерживаемая комбинация вернёт ошибку.

Названия `PF_INET`, `PF_INET6` и другие `PF_*` исторически обозначали *protocol family*. В Linux их значения совпадают с соответствующими `AF_*`; в прикладном коде обычно используют `AF_*`.

## Как сокет представлен в Linux

В user space сокет выглядит как обычный **файловый дескриптор** — целое число. В ядре за ним находится несколько связанных структур:

```text
файловый дескриптор
  ↓
struct file
  ↓
struct socket          общий объект Socket API
  ↓
struct sock            общая сетевая часть
  ↓
struct inet_sock       IP-адреса и порты
  ├─ struct inet_connection_sock
  │    └─ struct tcp_sock   состояние TCP
  └─ struct udp_sock        параметры UDP
```

- `struct socket` связывает сокет с файловой системой и операциями `bind`, `connect`, `sendmsg`, `recvmsg`.
- `struct sock` хранит общие очереди, буферы, блокировки, ошибки и указатель на реализацию протокола.
- `struct inet_sock` добавляет локальный и удалённый IP-адрес, локальный и удалённый порт.
- `struct inet_connection_sock` добавляет общую основу протоколов с соединением: таймеры, очередь запросов и accept queue.
- `struct tcp_sock` хранит состояние соединения, номера последовательности, `rwnd`, `cwnd`, SACK и очереди повторной передачи.
- `struct udp_sock` хранит дополнительные параметры UDP; состояния соединения TCP у него нет.

Основные определения находятся в `include/linux/net.h`, `include/net/sock.h`, `include/net/inet_sock.h`, `include/net/inet_connection_sock.h`, `include/linux/tcp.h` и `include/linux/udp.h`.

## Как ядро выбирает TCP или UDP

В `net/ipv4/af_inet.c` функция `inet_create()` обрабатывает создание `AF_INET`-сокета. Она выбирает две таблицы операций:

- `inet_stream_ops` и `tcp_prot` — для TCP;
- `inet_dgram_ops` и `udp_prot` — для UDP.

`struct proto_ops` описывает общий Socket API: `connect`, `accept`, `sendmsg`, `recvmsg`. `struct proto` указывает уже на реализацию конкретного протокола, например `tcp_sendmsg()` или `udp_sendmsg()`.

```text
socket(AF_INET, SOCK_STREAM, 0)
  ↓ net/socket.c
inet_create()
  ↓
inet_stream_ops + tcp_prot
```

Для IPv6 аналогичный выбор начинается в `net/ipv6/af_inet6.c`, но большая часть общей логики TCP всё равно переиспользуется из `net/ipv4`.

## Как сокет связывает TCP и IP при отправке

Пусть приложение создало TCP-сокет и вызвало `connect()`:

1. `bind()` или ядро назначает локальный IP и порт.
2. `connect()` записывает удалённый IP и порт и запускает TCP handshake.
3. `send()` находит сокет по файловому дескриптору и передаёт байты в его send buffer.
4. TCP использует состояние `struct tcp_sock`, создаёт сегменты и добавляет TCP-заголовок.
5. TCP передаёт сегмент IPv4 или IPv6 вместе с сокетом: IP использует его адреса, настройки и маршрут.
6. IP создаёт пакет и передаёт его драйверу.

```text
send(fd)
  ↓ struct socket → struct sock → struct tcp_sock
tcp_sendmsg() → tcp_write_xmit()
  ↓
ip_queue_xmit() → ip_output()
  ↓
драйвер сетевой карты
```

Сокет хранит контекст конечной точки, TCP отвечает за надёжный поток, а IP — за пакет и маршрут до другого устройства.

## Как входящий пакет находит сокет

1. IP проверяет заголовок и читает поле **Protocol / Next Header**.
2. Значение TCP передаёт содержимое в `tcp_v4_rcv()` или `tcp_v6_rcv()`, UDP — в `udp_rcv()`.
3. Транспортный протокол ищет сокет по сетевому пространству имён и набору адресов:

   ```text
   протокол + Source IP:Port + Destination IP:Port
   ```

4. TCP проверяет состояние, номера последовательности и ACK; UDP сразу ставит дейтаграмму в receive buffer.
5. Если процесс спит в `recv()`, ядро пробуждает его и копирует данные в user space.

Для TCP-сервера входящий SYN сначала находит **слушающий сокет** по локальному адресу и порту. Ядро создаёт состояние нового соединения, а `accept()` возвращает приложению отдельный файловый дескриптор подключённого сокета.

## Использование в user space

### TCP-клиент

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);
connect(fd, ...);
send(fd, data, size, 0);
recv(fd, buffer, size, 0);
close(fd);
```

TCP предоставляет поток байтов: границы отдельных вызовов `send()` не обязаны сохраниться в `recv()`.

### TCP-сервер

```text
socket() → bind() → listen() → accept()
                           ↓
                     recv() / send()
```

Слушающий сокет принимает новые соединения, а `accept()` создаёт новый дескриптор для общения с конкретным клиентом.

### UDP

```c
int fd = socket(AF_INET, SOCK_DGRAM, 0);
sendto(fd, data, size, 0, ...);
recvfrom(fd, buffer, size, 0, ...);
close(fd);
```

UDP сохраняет границы дейтаграмм. `connect()` для UDP тоже возможен, но он лишь закрепляет адрес получателя и фильтрует входящие дейтаграммы — handshake не появляется.

## Не каждый IP-пакет связан с сокетом

Сокет нужен, когда локальное приложение создаёт или получает сетевые данные. Если Linux работает как роутер, пересылаемый IP-пакет проходит через таблицу маршрутизации и `ip_forward()` без TCP- или UDP-сокета на этом роутере.

```text
локальная конечная точка: приложение ↔ сокет ↔ TCP/UDP ↔ IP
роутер:                   входящий IP → маршрутизация → исходящий IP
```
