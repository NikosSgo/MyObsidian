**ARP Address Resolution Protocol**  сопоставляет IPv4-адрес следующего узла с его MAC-адресом в текущей локальной сети.

```text
IP next hop:  192.168.1.1
        ↓ ARP
MAC next hop: AA:BB:CC:DD:EE:FF
```

ARP не выбирает маршрут и не ищет сервер в Интернете. Сначала таблица маршрутизации выбирает **следующий IP-узел**, затем ARP узнаёт его MAC, чтобы Ethernet/Wi‑Fi мог создать кадр.

## Зачем нужен ARP

IP-пакет содержит IP назначения. Но на текущем Ethernet- или Wi‑Fi-сегменте кадр отправляется по MAC-адресу.

```text
IP-пакет:          IP назначения = 8.8.8.8
Ethernet-кадр:     MAC назначения = MAC шлюза
```

Коммутатор не смотрит IP `8.8.8.8`: он видит MAC назначения и выбирает порт по своей MAC-таблице. Поэтому отправителю нужен MAC следующего узла.

## Алгоритм работы

Пусть ПК `192.168.1.10` хочет отправить пакет на шлюз `192.168.1.1`.

1. ОС проверяет ARP-кэш. Если там есть `192.168.1.1 → AA:BB:CC:DD:EE:FF`, сразу формируется обычный unicast-кадр.
2. Если записи нет, ПК отправляет **ARP Request** broadcast-кадром:

```text
Ethernet MAC назначения: FF:FF:FF:FF:FF:FF
Ethernet MAC источника:  MAC ПК

ARP: «Кто имеет IP 192.168.1.1?
      Сообщите 192.168.1.10»
```

3. Коммутатор рассылает broadcast по всем портам текущей VLAN, кроме входного.
4. Только устройство с IP `192.168.1.1` отвечает **ARP Reply** обычно unicast-кадром:

```text
192.168.1.1 → AA:BB:CC:DD:EE:FF
```

5. ПК сохраняет запись в ARP-кэше и отправляет исходный IP-пакет в кадре на этот MAC.

```text
[ MAC шлюза | MAC ПК | EtherType IPv4 | IP-пакет | FCS ]
```

## Один ARP-запрос — только в одной LAN

ARP Request — L2-broadcast. Роутеры не пересылают его в другие сети, поэтому ARP работает только в текущем broadcast-домене/VLAN.

| Куда идёт IP-пакет | Какой IP спрашивает ARP |
| --- | --- |
| Узел в той же подсети | IP конечного узла |
| Удалённая сеть | IP шлюза по умолчанию / выбранного next hop |

Пример удалённого сайта:

```text
цель IP-пакета:       93.184.216.34
маршрут выбрал:        шлюз 192.168.1.1
ARP спрашивает:        «кто имеет 192.168.1.1?»
MAC назначения кадра:  MAC шлюза
```

ПК никогда не ищет через ARP MAC удалённого сайта: его MAC существует в другой LAN и недоступен из текущей сети.

## Формат ARP-сообщения

ARP переносится внутри Ethernet-кадра с EtherType `0x0806`.

```text
Hardware type       тип L2-сети, для Ethernet = 1
Protocol type       тип L3-протокола, для IPv4 = 0x0800
Hardware size       длина MAC = 6 байт
Protocol size       длина IPv4 = 4 байта
Opcode              1 = Request, 2 = Reply
Sender MAC / IP     MAC и IP отправителя
Target MAC / IP     MAC и IP искомого узла
```

В ARP Request MAC цели ещё неизвестен, поэтому поле Target MAC обычно заполнено нулями.

## ARP-кэш

ARP-кэш хранит временные пары `IPv4 → MAC`. Он нужен, чтобы не делать broadcast перед каждым пакетом. Динамические записи имеют время жизни и затем обновляются; статические записи задаются вручную.

```text
192.168.1.1   → AA:BB:CC:DD:EE:FF   dynamic
192.168.1.20  → 11:22:33:44:55:66   dynamic
```

Часто ОС получает запись об отправителе уже из любого ARP-пакета, не только из ответа на свой запрос.

## Особые варианты

- **Gratuitous ARP** — устройство объявляет собственную пару IP/MAC без запроса. Используется при смене MAC, проверке конфликта IP и отказоустойчивом переключении.
- **Proxy ARP** — роутер отвечает на ARP-запрос от имени другого узла. Отправитель думает, что цель в его LAN, и посылает кадры роутеру. Применяется редко и усложняет сеть.

## Безопасность

В обычном ARP нет проверки, что ответ действительно прислал владелец IP. Злоумышленник может отправить ложную пару `IP шлюза → свой MAC` — это **ARP spoofing/poisoning**. Тогда трафик попадёт к нему (атака «человек посередине») или перестанет доходить.

Защита в коммутаторах: DHCP snooping + Dynamic ARP Inspection, привязка портов к MAC/IP, сегментация VLAN. Шифрование TLS защищает содержимое HTTP-трафика даже при перехвате, но не отменяет саму проблему подмены пути.

## ARP и IPv6

ARP существует только для IPv4. В IPv6 соответствие IPv6-адреса и MAC-адреса выполняет **NDP** (*Neighbor Discovery Protocol*) поверх ICMPv6; вместо Ethernet-broadcast он использует multicast.
