HATEOAS (Hypermedia As The Engine Of Application State) — это одно из ограничений архитектурного стиля REST.

Суть проста: сервер в своих ответах передаёт не только данные, но и ссылки (hypermedia), которые описывают, какие действия клиент может выполнить дальше. Клиент не должен «знать» заранее все URL и переходы — он следует по ссылкам, полученным от сервера.

Как это выглядит концептуально. Клиент запрашивает ресурс. Сервер возвращает представление ресурса и набор ссылок с отношениями (rel), например: self, update, delete, next, cancel. Клиент, анализируя эти ссылки, понимает доступные переходы и действия.

Пример в HTTP/JSON. Допустим, есть ресурс заказа:

Ответ без HATEOAS:  
```json
{  
"id": 42,  
"status": "created",  
"total": 100  
}
```

Клиенту нужно «знать», что дальше делать и по каким URL.

Ответ с HATEOAS:  
```json
{  
"id": 42,  
"status": "created",  
"total": 100,  
"_links": {  
"self": { "href": "/orders/42" },  
"pay": { "href": "/orders/42/pay", "method": "POST" },  
"cancel": { "href": "/orders/42/cancel", "method": "POST" }  
}  
}
```

Здесь сервер явно говорит: заказ можно оплатить или отменить, и как именно это сделать.

Зачем это нужно. Во-первых, слабая связность клиента и сервера: сервер может менять URL и бизнес-логику переходов без обновления клиента. Во-вторых, более строгий REST: состояние приложения управляется гипермедиа, а не жёстко прошитой логикой на клиенте. В-третьих, удобство для generic-клиентов, автодокументации и API-навигации.

Минусы и реальность использования. Реализация усложняет API и ответы. Большинство фронтенд-клиентов и мобильных приложений всё равно жёстко знают маршруты. Поэтому в «обычных» JSON-API HATEOAS часто либо игнорируют, либо используют частично (links без полной семантики состояний).

Где реально встречается. Spring HATEOAS (Java-мир), HAL, JSON:API (links), Siren. В FastAPI и большинстве Python-проектов используется редко, обычно ограничиваются явными эндпоинтами и OpenAPI.
