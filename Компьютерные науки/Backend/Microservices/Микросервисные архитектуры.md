# Микросервисные архитектуры

## Определение

**Микросервисная архитектура** — подход, при котором приложение состоит из множества небольших, независимых сервисов, каждый реализует одну бизнес-функцию и.deployable отдельно.

## Преимущества

| Преимущество | Пояснение |
|--------------|-----------|
| **Масштабируемость** | Каждый сервис масштабируется независимо |
| **Технологическая гетерогенность** | Разные сервисы — разные стеки (Java, Go, Python) |
| **Изоляция сбоев** | Падение одного сервиса не ломает всю систему |
| **Независимый деплой** | Обновления одного сервиса не требуют redeploy всей системы |
| **Организационная масштабируемость** | Команды работают автономно |

## Недостатки

| Недостаток | Пояснение |
|------------|-----------|
| **Распределённая сложность** | Мониторинг, трассировка, логирование |
| **Сетевые задержки** | Межсервисное взаимодействие через сеть |
| **Распределённые транзакции** | Согласованность через Saga, eventual consistency |
| **Дублирование логики** | Каждый сервис может реализовать свою инфраструктуру |
| **Сложность развёртывания** | Оркестрация контейнеров, сервис-меш |

## Сравнение с монолитом

| Критерий | Монолит | Микросервисы |
|----------|---------|--------------|
| Структура | Единый кодовая база | Множество сервисов |
| Деплой | Единый артефакт | Отдельные контейнеры |
| Масштабирование | Вертикальное + горизонтальное | Горизонтальное по компонентам |
| Технология | Один стек | Множество стеков |
| Начальная сложность | Низкая | Высокая |
| Подходит для | MVP, простые приложения | Крупные, растущие системы |

## Паттерны взаимодействия

- **Синхронный:** REST, gRPC
- **Асинхронный:** Очереди (Kafka, RabbitMQ)
- **Saga:** Управление распределёнными транзакциями через компенсирующие действия
- **API Gateway:** Единая точка входа (Kong, Traefik)

## Когда использовать

✅ Масштабируемая система, несколько команд, разные requirements на компоненты
❌ MVP, маленькая команда, простая бизнес-логика
