**Apache Kafka** — это распределенный, отказоустойчивый брокер сообщений с хранением на диске, предназначенный для обработки высоких нагрузок в реальном времени.

## Ключевая модель

- **Брокер (Broker)** — сервер в кластере Kafka, который хранит данные и обрабатывает запросы на чтение/запись. 
- **Тема (Topic)** — логическая категория, в которую продюсеры отправляют сообщения, а консьюмеры читают.
- **Партиция (Partition)** — физическая единица хранения внутри темы. Каждая партиция — это упорядоченный, неизменяемый лог с уникальным смещением. Одна тема может иметь десятки или сотни партиций.
- **Смещение (Offset)** — уникальный идентификатор сообщения внутри партиции (монотонно возрастающее 64-битное число).
- **Реплика (Replica)** — копия партиции на другом брокере, обеспечивающая отказоустойчивость. Каждая партиция имеет одного лидера (leader) и несколько последователей (followers).
- **Продюсер (Producer)** — клиент, публикующий сообщения в топики.
- **Консьюмер (Consumer)** — клиент, читающий сообщения из топиков.
- **Группа консьюмеров (Consumer Group)** — набор консьюмеров, которые совместно читают партиции темы (каждая партиция назначается только одному консьюмеру в группе).

## Протокол Kafka

Kafka использует свой собственный бинарный TCP-протокол. Все запросы и ответы построены вокруг отправки **запросов (Requests)** и получения **ответов (Responses)**.

### Типы запросов (основные команды протокола)

| Запрос | Код | Описание |
| :--- | :--- | :--- |
| **`Produce`** | 0 | Публикация сообщений в одну или несколько партиций |
| **`Fetch`** | 1 | Чтение сообщений из партиций (используется консьюмерами) |
| **`ListOffsets`** | 2 | Получение доступных смещений в партиции |
| **`Metadata`** | 3 | Запрос метаданных о кластере (список брокеров, партиций, лидеров) |
| **`OffsetCommit`** | 8 | Сохранение позиции консьюмера (для группы) |
| **`OffsetFetch`** | 9 | Получение сохраненной позиции консьюмера |
| **`JoinGroup`** | 11 | Вход консьюмера в группу (для балансировки) |
| **`Heartbeat`** | 12 | Поддержание активности консьюмера в группе |
| **`LeaveGroup`** | 13 | Выход консьюмера из группы |
| **`SyncGroup`** | 14 | Синхронизация назначения партиций в группе |
| **`DescribeGroups`** | 15 | Информация о группах консьюмеров |
| **`ApiVersions`** | 18 | Запрос поддерживаемых версий протокола |
| **`CreateTopics`** | 19 | Создание топиков |
| **`DeleteTopics`** | 20 | Удаление топиков |
| **`AddPartitionsToTxn`** | 24 | Добавление партиций в транзакцию (идемпотентность) |
| **`AddOffsetsToTxn`** | 25 | Добавление смещений в транзакцию |
| **`EndTxn`** | 26 | Завершение транзакции |
| **`Produce`** с транзакциями | - | Атомарная запись в несколько партиций |

### Общая структура запроса

| Размер (байт)  | 4            | 2               | 2               | 4                 | Переменный              |
| :------------- | :----------- | :-------------- | :-------------- | :---------------- | :---------------------- |
| **Содержимое** | **Длина запроса** | **ID API**      | **Версия API**  | **ИД корр.</sup> | **Данные запроса**      |
|                | (size)       | (api_key)       | (api_version)   | (correlation_id)  | (request_data)          |

**Пояснения:**
- **Длина запроса** — общий размер запроса в байтах (не включая само поле длины).
- **ID API** — числовой идентификатор команды (см. таблицу выше).
- **Версия API** — версия протокола для данной команды (поддержка обратной совместимости).
- **ИД корреляции** — уникальный ID, который связывает запрос с ответом (клиент сопоставляет их по этому полю).
- **Данные запроса** — параметры конкретной команды (например, для Produce — список тем, партиций и сообщений).

## Разбор последовательности для отправки сообщения (Produce Request)

Процесс отправки одного сообщения в Kafka — это отправка одного запроса `Produce`, который может содержать несколько сообщений в нескольких партициях (пакетная запись).

### Структура запроса `Produce`

```text
┌──────────────────────────────────────────────────────────────────┐
│  4 байта    │  2 байта  │  2 байта  │  4 байта  │  Переменный    │
│  Длина      │  API=0    │  Версия   │  Корреляция│  Данные       │
│  (size)     │  (Produce)│  (>= 0)   │  (ID)     │  (запрос)      │
└──────────────────────────────────────────────────────────────────┘
```

**Данные запроса `Produce` (основные поля):**

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│  transaction_id (nullable)  │  acks (2 байта)  │  timeout (4 байта)         │
├─────────────────────────────────────────────────────────────────────────────┤
│  topic_data (массив тем)                                                    │
│    ├── topic_name (строка)                                                  │
│    └── partition_data (массив партиций)                                     │
│        ├── partition_index (4 байта)                                        │
│        └── records (сообщения)                                              │
│            ├── длина сообщения (4 байта)                                    │
│            ├── CRC32 (4 байта)                                              │
│            ├── магический байт (version)                                    │
│            ├── атрибуты (сжатие, timestamp type, транзакционные флаги)      │
│            ├── timestamp (8 байт)                                           │
│            ├── ключ (bytes)                                                 │
│            └── значение (bytes)                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Разбор полей запроса `Produce`:

**1. Заголовок запроса (общий для всех команд)**
- `transaction_id` — ID транзакции (для идемпотентных продюсеров).
- `acks` — уровень подтверждения (`0`, `1`, `-1`/`all`):
  - `0` — брокер не ждет подтверждения (fire-and-forget).
  - `1` — лидер партиции подтверждает запись в свой лог.
  - `-1` или `all` — лидер ждет подтверждения от всех реплик (в зависимости от `min.insync.replicas`).
- `timeout` — время ожидания ответа от брокера в миллисекундах.

**2. Данные тем и партиций**
- Каждая тема может содержать несколько партиций для отправки.
- Для каждой партиции передается список сообщений (пакетно).

**3. Сообщение (Record)**
Внутри партиции каждое сообщение имеет структуру:

```text
┌────────────┬──────────┬──────────┬────────────┬──────────┬─────────┬──────────┐
│ Длина (4б) │  CRC (4б)│ Магия    │ Атрибуты   │ Время    │ Ключ    │ Значение │
│            │          │ (1б)     │ (1б)       │ (8б)     │ (bytes) │ (bytes)  │
└────────────┴──────────┴──────────┴────────────┴──────────┴─────────┴──────────┘
```

| Поле | Размер | Описание |
| :--- | :--- | :--- |
| **Длина** | 4 байта | Общая длина сообщения в байтах |
| **CRC32** | 4 байта | Контрольная сумма для проверки целостности |
| **Магия** | 1 байт | Версия формата сообщения (0, 1 или 2) |
| **Атрибуты** | 1 байт | Флаги: сжатие (0=нет, 1=gzip, 2=snappy, 3=lz4, 4=zstd), timestamp type (0=create time, 1=append time), транзакционные флаги |
| **Timestamp** | 8 байт | Временная метка в миллисекундах с эпохи Unix |
| **Ключ** | Переменный | Опциональный ключ (используется для маршрутизации по партициям) |
| **Значение** | Переменный | Само тело сообщения (payload) |

## Разбор последовательности для чтения сообщения (Fetch Request)

Консьюмер читает сообщения, отправляя запрос `Fetch`.

### Структура запроса `Fetch`

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│  replica_id (4б) │  max_wait_ms (4б) │  min_bytes (4б) │  max_bytes (4б)    │
├─────────────────────────────────────────────────────────────────────────────┤
│  topics (массив)                                                            │
│    ├── topic_name (строка)                                                  │
│    └── partitions (массив)                                                  │
│        ├── partition_index (4б)                                             │
│        ├── current_leader_epoch (4б)                                        │
│        └── fetch_offset (8б) — смещение, с которого начинать чтение         │
│             + log_start_offset (8б) — минимальное доступное смещение        │
└─────────────────────────────────────────────────────────────────────────────┘
```

| Поле | Описание |
| :--- | :--- |
| **replica_id** | -1 для обычного консьюмера, или ID брокера для репликации |
| **max_wait_ms** | Максимальное время ожидания, если данных меньше `min_bytes` |
| **min_bytes** | Минимальное количество данных, которое консьюмер готов получить (для эффективности) |
| **max_bytes** | Максимальный размер ответа (защита от переполнения) |
| **fetch_offset** | Смещение, с которого нужно читать (консьюмер сам его хранит) |

### Структура ответа на `Fetch`

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│  throttle_time_ms (4б) — время задержки (для ограничения скорости)          │
├─────────────────────────────────────────────────────────────────────────────┤
│  topics (массив)                                                            │
│    ├── topic_name                                                           │
│    └── partitions (массив)                                                  │
│        ├── partition_index (4б)                                             │
│        ├── error_code (2б) — 0 = успех                                      │
│        ├── high_watermark (8б) — последнее смещение, записанное лидером     │
│        ├── log_start_offset (8б) — минимальное доступное смещение           │
│        └── records (сообщения) — байтовый массив с сообщениями              │
└─────────────────────────────────────────────────────────────────────────────┘
```

## Потоки данных и управление группой консьюмеров

Для координации группы консьюмеров используется отдельный протокол:

1. **`JoinGroup`** — консьюмер сообщает, что хочет присоединиться к группе.
2. **Лидер группы** (первый присоединившийся) получает список всех консьюмеров и назначает партиции с помощью стратегии (Range, RoundRobin, Sticky, Cooperative).
3. **`SyncGroup`** — лидер отправляет назначение всем консьюмерам в группе.
4. **`Heartbeat`** — консьюмеры периодически отправляют heartbeat, чтобы подтвердить, что они живы (сессия expires через `session.timeout.ms`).
5. **Перебалансировка (Rebalance)** — если консьюмер уходит или добавляется, процесс повторяется.

## Формат ответа (общая структура)

Все ответы в Kafka имеют общий заголовок:

```text
┌──────────────┬────────────────────┬──────────────────────┐
│  Длина (4б)  │  Корреляция (4б)   │  Данные ответа       │
│              │  (correlation_id)  │  (зависит от API)    │
└──────────────┴────────────────────┴──────────────────────┘
```

**Пояснения:**
- `correlation_id` совпадает с ID, отправленным в запросе, чтобы клиент мог сопоставить ответ с запросом.
- Данные ответа зависят от типа запроса. Например, для `Produce` ответ содержит:
  - `throttle_time_ms` — время задержки (если брокер перегружен).
  - Массив результатов по партициям с полями:
    - `partition_index`
    - `error_code` (0 = успех, иначе код ошибки)
    - `base_offset` — смещение, с которого записано сообщение.
