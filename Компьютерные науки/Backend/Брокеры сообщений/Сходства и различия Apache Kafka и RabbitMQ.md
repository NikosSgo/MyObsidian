Несмотря на абсолютно разную архитектуру, у них есть общая база, как у брокеров сообщений:

| Характеристика                   | Описание                                                                                                                                                                        |
| :------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Асинхронная связь**            | Обе системы позволяют приложениям обмениваться данными асинхронно, развязывая отправителей и получателей во времени. Отправитель не ждет, пока получатель обработает сообщение. |
| **Модель "Издатель-Подписчик"**  | В обоих случаях есть продюсеры (издатели), которые отправляют сообщения, и консьюмеры (подписчики), которые их получают.                                                        |
| **Надежность доставки**          | Обе системы предоставляют гарантии доставки (at-least-once, exactly-once) и механизмы подтверждения (acknowledgements).                                                         |
| **Персистентность (сохранение)** | Обе могут сохранять сообщения на диск, чтобы пережить перезапуск брокера.                                                                                                       |
| **Кластеризация**                | Обе системы поддерживают работу в кластере из нескольких узлов для отказоустойчивости и масштабирования.                                                                        |
| **Маршрутизация**                | Обе имеют механизмы для направления сообщений по определенным темам или ключам.                                                                                                 |
| **Клиенты для языков**           | Для обеих систем существуют официальные и сторонние клиентские библиотеки для большинства популярных языков программирования.                                                   |

## Ключевые различия (сравнительная таблица)

| Критерий                         | **Apache Kafka**                                                                                                                      | **RabbitMQ (AMQP)**                                                                                                        |
| :------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------- |
| **Основная модель**              | **Распределенный лог (commit log)**. Сообщения — это записи в бесконечном журнале.                                                    | **Умный брокер / тупой потребитель** с очередями и обменниками.                                                            |
| **Центральная сущность**         | **Топик**, разделенный на **партиции**. Именно партиции обеспечивают параллелизм.                                                     | **Очередь**. Все сообщения хранятся в очередях, пока их не заберут.                                                        |
| **Маршрутизация**                | **Простая**. По ключу (key) сообщения определяется партиция. Нет гибкой логики маршрутизации.                                         | **Гибкая (4 типа обменников)**. Direct, Fanout, Topic, Headers — можно строить сложные схемы доставки.                     |
| **Удаление сообщений**           | **По времени (retention) или размеру**. Сообщения не удаляются после прочтения. Все хранятся заданное время.                          | **Сразу после подтверждения (ack)**. Как только консьюмер подтвердил обработку, сообщение удаляется из очереди.            |
| **Модель потребления**           | **Pull**. Консьюмер сам забирает сообщения из партиций, контролируя скорость.                                                         | **Push**. Брокер сам отправляет (толкает) сообщения консьюмеру.                                                            |
| **История / Повторный просмотр** | **Да**. Можно перечитать любое сообщение из истории (с любого смещения) сколько угодно раз.                                           | **Нет**. Если сообщение уже было получено и подтверждено, его больше нельзя прочитать.                                     |
| **Порядок сообщений**            | **Гарантируется в рамках одной партиции**. Сообщения с одинаковым ключом попадают в одну партицию и читаются по порядку.              | **Гарантируется в рамках одной очереди** (если консьюмер один).                                                            |
| **Масштабирование**              | **Горизонтальное**. Масштабируется за счет добавления брокеров и увеличения числа партиций.                                           | **Вертикальное**. Хотя кластер есть, горизонтальное масштабирование очередей сложнее (обычно увеличивают память/CPU).      |
| **Что масштабируется**           | **Пропускная способность (Throughput)**. Kafka может обрабатывать миллионы сообщений в секунду.                                       | **Количество подключений и гибкость маршрутизации**. RabbitMQ лучше держит десятки тысяч подключений.                      |
| **Протокол**                     | Собственный бинарный TCP-протокол (Kafka Protocol).                                                                                   | AMQP (0-9-1, 1.0) + MQTT, STOMP через плагины.                                                                             |
| **Хранение**                     | Хранит **все** сообщения на диске, даже самые свежие. Это основа его архитектуры.                                                     | Хранит в основном в **ОЗУ**, сбрасывая на диск при переполнении. Оптимизирован под быструю обработку.                      |
| **Группы потребителей**          | **Есть**. Позволяет нескольким консьюмерам делить нагрузку по партициям (каждая партиция читается только одним консьюмером в группе). | **Нет**. Каждый консьюмер получает свою копию сообщения из очереди, или несколько консьюмеров соревнуются за одну очередь. |
| **Типичная задержка**            | **Высокая** (десятки-сотни мс). Оптимизирован под пропускную способность, а не под низкую задержку.                                   | **Низкая** (микросекунды-миллисекунды). Оптимизирован под быструю доставку.                                                |

## Идеальные сценарии использования

| **Apache Kafka** | **RabbitMQ** |
| :--- | :--- |
| **Потоковая обработка данных в реальном времени** (аналитика, метрики, логи). | **Традиционные корпоративные очереди задач** (Background Job Processing). |
| **Хранилище событий (Event Sourcing)**, где важна история изменений. | **RPC (удаленный вызов процедур)** — запрос-ответ между микросервисами. |
| **Конвейеры данных (Data Pipelines)**, интеграция между множеством систем. | **Веб-приложения**, где нужна маршрутизация по сложным правилам. |
| **Системы, которым нужна возможность "переиграть" (replay) события**. | **Системы с большим количеством разнородных потребителей**, которым нужна гибкая маршрутизация. |
| **Задачи с очень высокой пропускной способностью** (логи от тысяч серверов). | **Задачи, где критична низкая задержка** (например, мгновенные уведомления). |
| **Долгосрочное хранение данных**. | **Временное хранение задач до их выполнения**. |

## Пример выбора (для наглядности)

**Выбираем Kafka, если:**
- Вам нужно обрабатывать 1+ миллион сообщений в секунду.
- Вам важно хранить историю сообщений для последующего анализа.
- У вас есть несколько независимых систем, которые должны читать одни и те же данные в своем темпе.
- Вы строите систему, основанную на событиях (Event-Driven Architecture).

**Выбираем RabbitMQ, если:**
- Вам нужна сложная маршрутизация (например, отправлять сообщение в разные очереди в зависимости от заголовка).
- Вам нужна максимально низкая задержка (RPC, мгновенные уведомления).
- У вас классическое приложение с задачами, которые нужно распределить между несколькими воркерами.
- Вы не хотите хранить историю, а нужно быстро обработать и забыть сообщение
