**IServiceProvider — это минималистичный контракт, намеренно оставленный примитивным.** Его единственный метод `GetService(Type)` отражает философию минимальной достаточности: контейнер должен уметь разрешать зависимости, но не управлять их жизненным циклом или конфигурацией. Эта примитивность — не недостаток, а архитектурное решение, оставляющее сложность на уровне реализации, а не интерфейса.

**Расширения IServiceProvider существуют как статические методы в `ServiceProviderServiceExtensions`**, превращая рутинные операции в типобезопасный API. `GetService<T>()` и `GetRequiredService<T>()` — не просто generic-обёртки, они инкапсулируют семантику: первый допускает отсутствие сервиса (возвращая null), второй гарантирует его наличие (кидая исключение). Это принудительное различие заставляет разработчика явно выбирать стратегию обработки отсутствующих зависимостей.

**Продвинутые расширения** вроде `GetServices<T>()` для разрешения коллекций или `CreateScope()` для создания областей видимости демонстрируют важный принцип: IServiceProvider — это фабрика фабрик. Каждый вызов порождает новые объекты или контексты, управляя не только инстанцированием, но и временем жизни через неявную привязку к корневому контейнеру или scope.

```csharp
// Под капотом GetRequiredService — не просто каст
public static T GetRequiredService<T>(this IServiceProvider provider)
{
    var service = provider.GetService(typeof(T));
    if (service == null)
        throw new InvalidOperationException($"No service for type {typeof(T)}");
    return (T)service; // Гарантия ненулевого возврата
}
```

**Системные расширения** вроде `GetService<ILogger<T>>()` в ASP.NET Core показывают, как минималистичный интерфейс становится точкой интеграции для сложных систем. Фреймворк регистрирует фабрики, которые динамически создают сервисы на основе контекста вызова (типа T в ILogger<T>), превращая простой GetService в мощный механизм контекстно-зависимого разрешения.

**Критически важное расширение — `CreateScope()`**, которое трансформирует статический контейнер в динамическую систему с управляемым временем жизни. Оно не просто создаёт новый IServiceProvider, а устанавливает иерархию: корневой контейнер владеет singleton'ами, дочерний scope — своими scoped-сервисами, с чётким контрактом на освобождение ресурсов через IDisposable.

**Эволюция этих расширений** показывает движение от Service Locator антипаттерна к явному внедрению зависимостей. Современные практики избегают прямого использования IServiceProvider, кроме точек входа (factories, hosted services), где зависимость должна создаваться динамически. Расширения же остаются мостом между минималистичным ядром DI и потребностями реальных приложений, добавляя безопасность и удобство без изменения фундаментального контракта.
