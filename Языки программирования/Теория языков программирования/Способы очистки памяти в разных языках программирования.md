**Управление памятью** — это определение момента, когда выделенная объекту память больше не нужна и может быть использована повторно.

Основные подходы:
- ручное выделение и освобождение памяти;
- детерминированное освобождение при выходе из области видимости — RAII;
- подсчёт ссылок;
- трассирующая сборка мусора;
- владение и заимствование с проверкой во время компиляции.

Нужно различать:
- **память** — участки оперативной памяти, занятые объектами;
- **внешние ресурсы** — файлы, сокеты, соединения с базой данных, блокировки, дескрипторы операционной системы.

Сборщик мусора знает, какие объекты в памяти достижимы, но обычно ничего не знает о правилах закрытия внешних ресурсов. Поэтому даже в языке с автоматической сборкой мусора файлы и соединения необходимо закрывать явно или через специальную конструкцию языка.

Освобождение объекта также не означает, что соответствующие страницы памяти немедленно возвращаются операционной системе. Среда выполнения или аллокатор могут сохранить их для последующих выделений внутри процесса.

### Основные модели

**Ручное управление** означает, что программист явно выделяет и освобождает динамическую память. Оно даёт полный контроль, но допускает:
- утечки памяти;
- повторное освобождение;
- обращение по висячему указателю;
- освобождение неправильным способом;
- повреждение памяти.

**RAII** — ресурс связывается со временем жизни объекта. Ресурс захватывается при создании объекта и освобождается его деструктором при выходе из области видимости. Момент очистки предсказуем, включая выход из функции из-за исключения.

**Подсчёт ссылок** хранит для объекта число владеющих ссылок. Когда счётчик становится равен нулю, объект можно уничтожить. Освобождение обычно происходит быстро и предсказуемо, но цикл сильных ссылок может сохранить уже недоступные объекты.

**Трассирующий сборщик мусора**, или GC, начинает с корней — локальных переменных активных вызовов, глобальных и статических ссылок, регистров и других объектов среды выполнения. Затем он обходит граф ссылок:
- достижимые объекты считаются живыми;
- недостижимые объекты считаются мусором;
- память мусора освобождается или используется повторно.

Основные техники трассирующей сборки:
- **mark-and-sweep** — отметить достижимые объекты и освободить неотмеченные;
- **копирующая сборка** — перенести живые объекты в другую область, оставив мусор;
- **уплотнение** — переместить живые объекты, устранив фрагментацию;
- **поколенческая сборка** — чаще проверять молодые объекты, поскольку большинство из них быстро становится мусором;
- **инкрементальная и конкурентная сборка** — выполнять часть работы небольшими этапами или параллельно с программой, уменьшая длительные остановки.

**Владение и заимствование** определяют владельца каждого значения и проверяют допустимость ссылок во время компиляции. Когда владелец исчезает, значение уничтожается. Этот подход позволяет обходиться без общего трассирующего GC.

### Python

Способ управления памятью зависит от реализации языка. Наиболее распространённая реализация **CPython** сочетает:
- подсчёт ссылок как основной механизм;
- дополнительный сборщик циклического мусора.

Каждая сильная ссылка увеличивает счётчик объекта. Когда последняя сильная ссылка исчезает, CPython обычно сразу уничтожает объект:

```python
data = [1, 2, 3]
alias = data

del data       # удалена только одна ссылка
del alias      # исчезла последняя ссылка
```

Оператор `del` не является командой освобождения объекта. Он удаляет имя, элемент коллекции или другую ссылку. Объект продолжает существовать, если на него ссылается что-то ещё.

Обычный подсчёт ссылок не обнаруживает циклы:

```python
class Node:
    pass

left = Node()
right = Node()
left.other = right
right.other = left
```

После удаления внешних ссылок объекты продолжают ссылаться друг на друга. Циклический GC CPython периодически обнаруживает такие недостижимые группы и освобождает их.

Модуль `gc` позволяет запускать сборку, изменять её параметры и исследовать циклические утечки. В обычной программе часто вызывать `gc.collect()` не следует: среда выполнения сама выбирает момент сборки.

Другие реализации Python могут использовать иную стратегию. Например, наличие подсчёта ссылок и немедленное уничтожение объекта не является универсальной гарантией самого языка Python.

Для внешних ресурсов используется контекстный менеджер:

```python
with open("data.txt", encoding="utf-8") as file:
    text = file.read()
```

Метод `__exit__` вызывается при выходе из блока даже при исключении. Поэтому `with` отвечает за своевременное закрытие ресурса, а GC — за память объекта.

### Java

Объекты Java обычно размещаются в управляемой куче JVM. Трассирующий сборщик начинает с **GC roots**, находит достижимые объекты и освобождает недостижимые.

В JVM доступны разные сборщики мусора. Они могут отличаться:
- пропускной способностью;
- продолжительностью остановок программы;
- использованием нескольких потоков;
- конкурентной обработкой;
- способом уплотнения памяти;
- поведением на маленьких и очень больших кучах.

Конкретный сборщик является свойством реализации и конфигурации JVM, а не семантики языка. Поэтому Java не гарантирует точный момент уничтожения объекта.

```java
Object value = new Object();
value = null;
```

Присваивание `null` лишь удаляет одну ссылку. Объект станет кандидатом на сборку, только если он больше недостижим из корней. Вызов `System.gc()` является запросом к JVM и не даёт гарантии немедленной сборки.

GC не защищает от логических утечек. Если ненужный объект всё ещё хранится в статической коллекции, кэше, слушателе событий или `ThreadLocal`, он остаётся достижимым и не может быть собран.

Для файлов и других ресурсов используется `try-with-resources`. Ресурс должен реализовывать `AutoCloseable`:

```java
try (var reader = Files.newBufferedReader(path)) {
    System.out.println(reader.readLine());
}
```

Метод `close()` вызывается при выходе из блока. Финализация и `Cleaner` не подходят для своевременного освобождения критических ресурсов, поскольку их запуск зависит от GC и может быть сильно отложен.

### C# и .NET

Объекты C# в управляемой куче очищает трассирующий поколенческий сборщик CLR. Основные поколения:
- поколение 0 — недавно созданные и обычно короткоживущие объекты;
- поколение 1 — промежуточное поколение;
- поколение 2 — долгоживущие объекты.

Объекты, пережившие сборку, могут быть перемещены в старшее поколение. Во время обычной сборки CLR отмечает живые объекты, освобождает мусор и при необходимости уплотняет память. Большие объекты размещаются в отдельной области — Large Object Heap.

Как и в Java, точный момент сборки не определён. `GC.Collect()` существует, но принудительный запуск без измеренной необходимости обычно ухудшает работу адаптивного сборщика.

Для внешних ресурсов применяется интерфейс `IDisposable` и конструкция `using`:

```csharp
using var reader = File.OpenText("data.txt");
string text = reader.ReadToEnd();
```

Компилятор преобразует `using` в вызов `Dispose()` внутри `finally`. Для асинхронно освобождаемых ресурсов существуют `IAsyncDisposable` и `await using`.

Финализатор вида `~ClassName()` вызывается сборщиком недетерминированно и используется только как резервный механизм для типов, непосредственно владеющих неуправляемым ресурсом. Для дескрипторов предпочтительнее `SafeHandle` и корректный шаблон `Dispose`.

Важно: GC не вызывает `Dispose()` автоматически только потому, что объект реализует `IDisposable`. Это обязанность использующего кода или конструкции `using`.

### C++

C++ не имеет обязательного общего сборщика мусора. Основная модель современного C++ — **RAII** и детерминированные деструкторы.

Локальный объект с автоматическим временем хранения уничтожается при выходе из области видимости:

```cpp
void process() {
    std::vector<int> values{1, 2, 3};
    std::ifstream file("data.txt");
} // вызываются деструкторы file и values
```

Деструкторы вызываются и при раскрутке стека из-за исключения. Поэтому один механизм управляет как памятью, так и файлами, блокировками, сокетами и другими ресурсами.

Память можно контролировать вручную:

```cpp
auto* value = new Widget();
delete value;
```

Для массива, созданного через `new[]`, требуется `delete[]`. Ошибка в паре выделения и освобождения приводит к неопределённому поведению. В прикладном C++ непосредственные `new` и `delete` стараются не использовать.

Предпочтительные средства:
- `std::vector`, `std::string` и другие контейнеры самостоятельно владеют памятью;
- `std::unique_ptr<T>` выражает единоличное владение;
- `std::shared_ptr<T>` использует подсчёт сильных ссылок;
- `std::weak_ptr<T>` не продлевает время жизни и разрывает циклы;
- `std::make_unique` и `std::make_shared` безопаснее непосредственного создания владеющего указателя.

```cpp
auto object = std::make_unique<Widget>();
```

Когда `object` выходит из области видимости, `Widget` уничтожается и память освобождается.

`shared_ptr` следует применять только при действительно совместном владении. Цикл из `shared_ptr` не обнуляет счётчики и создаёт утечку; обратную связь в таком графе обычно делают через `weak_ptr`.

C++ обеспечивает детерминированную очистку, но компилятор не предотвращает все ошибки владения. Сырые указатели, неправильное ручное освобождение и неверно спроектированное совместное владение остаются ответственностью программиста.

### Rust

Rust использует владение, заимствование и времена жизни. В стандартной модели у значения есть владелец. При передаче владение перемещается, а прежнюю переменную больше нельзя использовать:

```rust
let first = String::from("data");
let second = first;

// println!("{first}"); // ошибка: владение перемещено
```

Ссылки `&T` и `&mut T` заимствуют значение, но не владеют им. Компилятор проверяет, что ссылка не переживёт владельца и что правила совместного и изменяемого доступа не нарушены.

Когда владелец выходит из области видимости, Rust вызывает `Drop::drop`, затем уничтожает поля и освобождает принадлежащую объекту память:

```rust
{
    let values = vec![1, 2, 3];
} // values уничтожается здесь
```

Типы `Box<T>`, `Vec<T>` и `String` владеют динамической памятью. Для пользовательского ресурса можно реализовать трейт `Drop`:

```rust
impl Drop for Connection {
    fn drop(&mut self) {
        self.close();
    }
}
```

Обычно очистка детерминирована и не требует трассирующего GC. В отличие от C++, правила владения и заимствования проверяются компилятором, что предотвращает значительную часть обращений после освобождения, двойных освобождений и гонок данных.

Для совместного владения используются:
- `Rc<T>` — подсчёт ссылок в одном потоке;
- `Arc<T>` — атомарный подсчёт ссылок между потоками;
- `Weak<T>` — слабая ссылка, не удерживающая объект.

Цикл из `Rc` или `Arc` может создать утечку памяти. Rust считает утечку безопасной для памяти, поскольку она не приводит к обращению по недействительному адресу. Для обратных связей применяют `Weak`.

В блоках `unsafe` можно использовать сырые указатели и самостоятельно управлять памятью. Типы `ManuallyDrop` и функции наподобие `mem::forget` позволяют сознательно отключить обычное уничтожение, поэтому абсолютной невозможности утечек Rust не гарантирует.

### Другие интересные модели

**Swift** использует автоматический подсчёт ссылок — ARC. Компилятор вставляет операции увеличения и уменьшения счётчиков, а объект класса уничтожается после исчезновения последней сильной ссылки. Это даёт более предсказуемое освобождение, чем трассирующий GC, но сильные циклы необходимо разрывать ссылками `weak` или `unowned`.

**Go** использует трассирующий сборщик мусора, работающий совместно с программой. Программист обычно не управляет временем освобождения памяти. Конструкция `defer` применяется для детерминированного закрытия файлов, разблокировки мьютексов и других действий, но сама по себе не освобождает память объекта.

**JavaScript** использует автоматическую трассирующую сборку, конкретный алгоритм которой определяется движком. `WeakMap` и `WeakSet` не удерживают свои ключи сильной ссылкой. `WeakRef` и `FinalizationRegistry` позволяют ограниченно наблюдать сборку, но выполнение финализатора не гарантировано по времени и не должно использоваться для основной логики или критических ресурсов.

**Zig** не выполняет управление динамической памятью за программиста и не предоставляет единственный неявный глобальный аллокатор. Функции обычно получают объект `Allocator`, поэтому стратегия выделения становится явной частью интерфейса. Освобождение выполняется явно, а `defer` помогает привязать его к выходу из области видимости.

### Основные различия

- Python в CPython — подсчёт ссылок с дополнительным поиском циклов.
- Java и C# — недетерминированная трассирующая сборка, обычно организованная с учётом поколений объектов.
- C++ — детерминированный RAII, умные указатели и возможность полностью ручного управления.
- Rust — детерминированное владение и `Drop` с проверкой ссылок во время компиляции.
- Swift — автоматический подсчёт ссылок, чувствительный к циклам.
- Go и JavaScript — автоматическая трассирующая сборка, детали которой контролирует среда выполнения.
- Zig и C — явное управление через аллокаторы и ручное освобождение.

Автоматическое управление памятью не исключает утечек:
- трассирующий GC не удаляет ненужный, но всё ещё достижимый объект;
- подсчёт ссылок без дополнительного GC не удаляет сильные циклы;
- ручная модель допускает потерю последнего указателя на выделенную область;
- RAII не поможет, если владение выражено неправильно;
- Rust допускает циклы `Rc` и намеренные утечки;
- ни один GC не заменяет своевременное закрытие внешних ресурсов.

Выбор модели является компромиссом между безопасностью, предсказуемостью задержек, стоимостью среды выполнения, удобством программирования и степенью контроля над памятью.
