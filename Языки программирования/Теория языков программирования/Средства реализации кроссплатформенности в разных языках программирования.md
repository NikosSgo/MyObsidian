**Кроссплатформенность** — способность программы работать на нескольких сочетаниях операционной системы, аппаратной архитектуры и программной среды с минимальными изменениями исходного кода.

Платформа может включать:
- операционную систему — Windows, Linux, macOS, Android, iOS;
- архитектуру процессора — x86-64, ARM64, RISC-V;
- двоичный интерфейс приложений — ABI;
- формат исполняемого файла — PE, ELF, Mach-O;
- системные библиотеки и их версии;
- среду выполнения — JVM, .NET, Python, браузер;
- доступные системные и графические API.

Нужно различать несколько уровней переносимости:
- **переносимость исходного кода** — один код можно собрать или запустить на разных платформах;
- **переносимость промежуточного кода** — один байткод выполняется разными реализациями виртуальной машины;
- **переносимость бинарного файла** — один и тот же готовый файл запускается на разных платформах;
- **переносимость поведения** — программа не только запускается, но и одинаково работает с файлами, сетью, числами, потоками и интерфейсом.

Один исходный код обычно не означает один исполняемый файл. Нативные программы чаще требуется отдельно собирать для каждой комбинации операционной системы, архитектуры и ABI.

### Основные способы реализации

**Стандартизация языка и стандартной библиотеки** задаёт общие типы, операции и API. Если программа использует только стандартизированные возможности, её можно перенести на другую реализацию языка.

Стандарт не устраняет все различия. На платформах могут отличаться:
- размер и представление некоторых типов;
- порядок байтов;
- файловые пути и разделители;
- кодировки и локали;
- модель процессов и сигналов;
- сетевые возможности;
- точность времени;
- доступность потоков и атомарных операций.

**Интерпретатор** реализуется отдельно для каждой платформы и выполняет общий исходный или промежуточный код. Программа переносится вместе с требованием установить подходящую среду выполнения.

**Виртуальная машина** исполняет стандартизированный промежуточный код. Компилятор не обязан заранее знать конкретный процессор: преобразование в машинные инструкции выполняет интерпретатор или JIT-компилятор целевой виртуальной машины.

**Транспиляция** преобразует исходный код одного языка в другой переносимый язык, например в JavaScript. Дальнейшая переносимость определяется целевой средой.

**Кросс-компиляция** создаёт на одной платформе нативный код для другой. При этом различают:
- **host** — система, на которой работает компилятор;
- **target** — система, для которой создаётся программа.

Кросс-компилятору могут потребоваться целевые заголовки, библиотеки, системный корень, линкер и SDK.

**Условная компиляция** выбирает разные реализации для разных систем. Общий интерфейс остаётся единым, а платформенные детали изолируются:

```text
общий код
    ├── реализация для Windows
    ├── реализация для Linux
    └── реализация для macOS
```

**Кроссплатформенная библиотека или фреймворк** предоставляет единый API поверх разных системных API. Например, одна функция работы с окном может внутри вызывать Win32, Cocoa или Wayland/X11.

**Контейнеризация** переносит приложение вместе с пользовательским окружением и зависимостями. Однако контейнер не является универсальным бинарным форматом: образ зависит от архитектуры процессора и обычно использует ядро определённого семейства ОС.

**WebAssembly** предоставляет переносимый двоичный формат и изолированную вычислительную модель. Доступ к файлам, сети, интерфейсу и другим возможностям осуществляется через API среды выполнения, например Web API или WASI.

### Python

Python достигает кроссплатформенности за счёт реализаций интерпретатора для разных систем. Исходный файл `.py` обычно можно запустить в любой совместимой реализации Python:

```text
source.py → Python runtime для конкретной платформы → машинные инструкции
```

CPython предварительно компилирует модули во внутренний байткод и может сохранять его в `.pyc`. Этот байткод выполняет виртуальная машина CPython, но формат байткода является деталью реализации и может изменяться между версиями Python. Поэтому распространять исходный код или пакет надёжнее, чем считать `.pyc` универсальным форматом.

Средства переносимости Python:
- стандартная библиотека скрывает многие различия ОС;
- `pathlib` формирует пути без ручного выбора разделителя;
- `os`, `shutil`, `subprocess` предоставляют переносимые операции там, где это возможно;
- `sys.platform`, `os.name` и `platform` позволяют определить среду;
- условный импорт изолирует платформенный код;
- система пакетов учитывает версию Python, ABI, ОС и архитектуру.

```python
from pathlib import Path

config = Path.home() / ".my_app" / "config.json"
```

Чистый Python-пакет может распространяться как универсальный wheel с платформенным тегом `any`. Если пакет содержит расширение на C, C++ или Rust, нужен отдельный wheel для конкретных Python ABI и платформы.

```python
if sys.platform == "win32":
    from .windows_backend import Backend
else:
    from .posix_backend import Backend
```

Ограничения переносимости:
- системные команды и пути различаются;
- расширения на C используют платформенный ABI;
- не все библиотеки доступны на всех ОС;
- виртуальное окружение обычно нельзя просто скопировать между разными системами;
- наличие интерпретатора нужной версии остаётся внешней зависимостью.

Для автономной поставки применяют упаковщики, которые включают интерпретатор и зависимости. Такой пакет становится удобнее для пользователя, но обычно создаётся отдельно для каждой целевой ОС и архитектуры.

### Java

Компилятор Java преобразует исходный код в байткод JVM и файлы `.class`:

```text
.java → javac → .class → JVM целевой платформы → машинный код
```

Формат `class` и набор инструкций JVM не зависят от конкретного процессора и операционной системы. Реализация JVM создаётся отдельно для каждой платформы, а JIT-компилятор преобразует часто выполняемый байткод в нативный код текущего процессора.

Основные средства:
- стандартизированный байткод JVM;
- одинаковая модель типов и памяти JVM;
- стандартная библиотека Java;
- JAR-архивы для распространения классов и ресурсов;
- API `Path`, `Files`, `System` и другие платформенные абстракции;
- загрузка классов во время выполнения;
- тестирование одной сборки на разных реализациях JVM.

Фраза *write once, run anywhere* действует при наличии совместимой JVM и использовании переносимых API. Кроссплатформенность нарушают:
- JNI и нативные библиотеки;
- вызов системных команд;
- зависимость от конкретной файловой системы;
- использование внутренних API определённой JVM;
- различия графической среды, шрифтов и системных разрешений.

Нативная библиотека внутри Java-проекта должна поставляться отдельными вариантами, например для `windows-x86_64`, `linux-x86_64` и `macos-aarch64`.

### C# и .NET

Обычная управляемая сборка C# компилируется в **Common Intermediate Language**, или CIL, и метаданные:

```text
.cs → CIL-сборка → CLR целевой платформы → JIT → машинный код
```

CIL не привязан к процессору. Реализация .NET для конкретной системы содержит CLR, стандартные библиотеки и JIT-компилятор соответствующей архитектуры.

Варианты распространения .NET-приложения:
- **framework-dependent** — поставляется приложение, а совместимый .NET должен быть установлен отдельно;
- **self-contained** — вместе с приложением поставляется среда выполнения;
- **single-file** — файлы приложения упаковываются для удобства поставки;
- **Native AOT** — CIL заранее компилируется в нативный код.

Self-contained, single-file и Native AOT не создают универсальный бинарный файл. Публикация выполняется под конкретный **Runtime Identifier**, или RID:

```text
win-x64
linux-x64
linux-arm64
osx-arm64
```

```powershell
dotnet publish -c Release -r linux-x64 --self-contained true
```

Native AOT уменьшает зависимость от установленной среды и ускоряет запуск, но создаёт платформенно-зависимый исполняемый файл и ограничивает некоторые динамические возможности среды выполнения.

Переносимость поддерживают:
- общая базовая библиотека .NET;
- проверки `OperatingSystem.IsWindows()` и подобных условий;
- абстракции файловой системы, сети и процессов;
- многоплатформенные целевые фреймворки;
- RID-зависимые ресурсы NuGet-пакетов;
- условная компиляция и отдельные реализации интерфейсов.

```csharp
if (OperatingSystem.IsWindows())
{
    // платформенная реализация
}
```

Кроссплатформенность ограничивают P/Invoke, COM, реестр Windows, системные библиотеки и UI-фреймворки, доступные только на части платформ.

### C++

C++ обычно компилируется непосредственно в нативный код. Поэтому язык обеспечивает прежде всего переносимость исходного кода, но не готового бинарного файла:

```text
одни исходники
    ├── компилятор Windows → PE для Windows
    ├── компилятор Linux   → ELF для Linux
    └── компилятор macOS   → Mach-O для macOS
```

Стандарт C++ определяет синтаксис, семантику и стандартную библиотеку, но не устанавливает единый системный ABI и формат исполняемого файла.

Средства переносимости:
- стандартные контейнеры, алгоритмы, потоки и файловая система;
- типы фиксированной ширины из `<cstdint>`, когда ширина принципиальна;
- feature-test macros для проверки возможностей стандарта;
- условная компиляция;
- отдельный слой платформенной реализации;
- системы сборки CMake и Meson;
- кроссплатформенные библиотеки Qt, SDL, Boost и другие;
- кросс-компиляторы GCC и Clang.

```cpp
#if defined(_WIN32)
    // Windows
#elif defined(__linux__)
    // Linux
#elif defined(__APPLE__)
    // macOS или другая платформа Apple
#endif
```

Большое число подобных проверок по всему проекту ухудшает архитектуру. Обычно создают общий интерфейс и несколько файлов реализации, а система сборки выбирает нужный.

CMake не делает непереносимый код переносимым, но помогает:
- находить компилятор и библиотеки;
- выбирать исходные файлы;
- задавать платформенные параметры;
- создавать проекты для разных сборочных систем;
- выполнять кросс-компиляцию через toolchain-файл.

Главные источники проблем:
- различия компиляторов и ABI;
- порядок байтов и выравнивание структур;
- размер платформенно-зависимых типов;
- системные вызовы;
- динамические библиотеки и правила их поиска;
- неопределённое поведение, которое проявляется по-разному;
- зависимости, не собранные для целевой платформы.

### Rust

Rust, как и C++, обычно создаёт нативный бинарный файл для конкретной цели. Цель описывается **target triple**:

```text
x86_64-pc-windows-msvc
x86_64-unknown-linux-gnu
aarch64-apple-darwin
wasm32-unknown-unknown
```

Компоненты обозначают архитектуру, производителя или окружение, операционную систему и ABI. Один исходный проект можно собрать под несколько целей, но полученные файлы различаются.

```powershell
rustup target add x86_64-unknown-linux-gnu
cargo build --release --target x86_64-unknown-linux-gnu
```

Средства Rust:
- встроенное понятие целевой платформы;
- атрибуты `#[cfg(...)]` и макрос `cfg!`;
- target-зависимые модули и зависимости Cargo;
- стандартная библиотека с платформенными абстракциями;
- LLVM как многоплатформенная серверная часть компилятора;
- `no_std` для платформ без полноценной операционной системы;
- компиляция в WebAssembly;
- уровни официальной поддержки targets.

```rust
#[cfg(target_os = "windows")]
fn platform_name() -> &'static str {
    "Windows"
}

#[cfg(target_os = "linux")]
fn platform_name() -> &'static str {
    "Linux"
}
```

Наличие цели в `rustc` ещё не гарантирует полностью готовую кросс-сборку. Могут потребоваться:
- целевой линкер;
- системные библиотеки;
- SDK;
- совместимая стандартная библиотека;
- инструменты для сборки зависимостей на C и C++.

Чистый Rust переносится проще, чем проект с FFI. Вызовы C ABI, системных библиотек или платформенных crate требуют отдельных проверок и зависимостей.

### Другие интересные подходы

**Go** компилируется в нативный код, но инструменты языка непосредственно поддерживают множество комбинаций ОС и архитектур. Цель задают переменные `GOOS` и `GOARCH`:

```powershell
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go build
```

Для чистого Go кросс-компиляция обычно проста. Использование `cgo` добавляет зависимость от C-компилятора, системных библиотек и ABI целевой платформы. Условный код выбирается build constraints или именами файлов наподобие `file_windows.go`.

**JavaScript** переносится благодаря стандартизированному языку ECMAScript и средам выполнения в браузерах и на сервере. Однако JavaScript и конкретная платформа — не одно и то же:
- браузер предоставляет DOM, `window`, Web API и модель разрешений;
- Node.js предоставляет файловую систему, процессы и собственные модули;
- другие среды имеют другой набор host API.

Поэтому переносимость JavaScript обеспечивают проверка возможностей, полифилы, транспиляторы, кроссплатформенные библиотеки и разделение общего и платформенного кода. Проверка конкретного браузера обычно хуже проверки необходимой возможности.

**Kotlin Multiplatform** разделяет проект на общие и платформенные source sets. `commonMain` содержит переносимую логику, а `jvmMain`, `iosMain`, `jsMain` и другие части используют API конкретной цели. Механизм `expect/actual` позволяет объявить общий контракт и предоставить реализацию для каждой платформы.

Kotlin может компилироваться:
- в байткод JVM;
- в JavaScript;
- в WebAssembly;
- в нативный код через Kotlin/Native.

Это переносимость исходной логики, а не один универсальный результат компиляции.

**Dart и Flutter** используют общий язык и фреймворк, но создают разные артефакты для мобильных, настольных и веб-платформ. Flutter предоставляет единый набор виджетов и собственный слой отрисовки, а доступ к системным функциям реализуется платформенными плагинами. Общую логику и интерфейс можно разделять, но интеграции с ОС остаются платформенными.

**WebAssembly** является переносимой целью компиляции для Rust, C, C++, Go и других языков:

```text
исходный язык → .wasm → браузер или отдельная Wasm-среда
```

Модуль `.wasm` не получает произвольный доступ к операционной системе. Возможности предоставляет host-среда:
- в браузере — JavaScript и Web API;
- вне браузера — WASI или собственный интерфейс среды выполнения.

Такая модель повышает переносимость и изоляцию, но взаимодействие с платформой всё равно требует согласованного API.

### Что чаще всего нарушает переносимость

- нативная зависимость без сборки для нужной платформы;
- прямой вызов системного API;
- предположение о разделителе пути или регистре имён файлов;
- предположение о размере типа, порядке байтов или выравнивании;
- зависимость от конкретной оболочки и системной команды;
- различия кодировок, локалей и часовых поясов;
- GUI-фреймворк только для одной ОС;
- различия модели процессов, сигналов и прав доступа;
- сериализация сырого представления структуры;
- неполное тестирование на реальных целевых системах.

Для сохранения кроссплатформенности полезно:
- держать основную логику независимой от ОС;
- скрывать платформенные операции за интерфейсами;
- использовать стандартные типы и библиотеки;
- избегать ручного составления путей;
- явно определять форматы файлов и сетевых сообщений;
- проверять возможности платформы, а не только её название;
- собирать и тестировать проект в CI на всех поддерживаемых целях;
- документировать список поддерживаемых ОС, архитектур и версий среды.

Кроссплатформенность не является свойством только языка. Она получается из сочетания языка, стандартной библиотеки, среды выполнения, компилятора, системы сборки, зависимостей и архитектуры приложения.
